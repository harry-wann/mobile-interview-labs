交易所 App 架構設計:怎麼設計才合理

本章目標:面對「如果請你設計一個交易所 App,你會怎麼設計架構?」這題,能有條理地從需求特性 → 分層 → 模組 → 關鍵技術決策一路講下來。 這題沒有唯一標準答案,面試官看的是你有沒有章法:先講需求與限制,再講取捨。

1. 先講需求特性(回答的開場)

交易所 App 和一般 App 最大的不同,是這四個特性,每一條都直接決定架構:

特性 意義 對架構的影響
即時性 行情每秒多次更新、下單要快 需要 WebSocket 長連線 + 高效 UI 更新策略
正確性 錢不能錯、狀態不能亂 金額用 Decimal、單一資料真相來源、以伺服器為準
安全性 資產、個資 登入與 Token 管理、生物辨識、憑證固定、越獄偵測
穩定性 行情劇烈時流量暴增 斷線重連、降級策略、錯誤處理要是一等公民

面試開場範例:「我會先確認需求:交易所 App 的核心是行情、下單、資產三大功能,特性是即時、正確、安全。所以我的架構會圍繞『一條穩定的即時資料流』和『嚴格的分層隔離』來設計。」

2. 整體分層架構

圖例:🎨 UI 層=畫面與使用者互動|🧠 簡報層=畫面狀態與邏輯(ViewModel)|📦 領域層=業務規則,不依賴任何框架|💾 資料層=決定資料從哪來(網路/快取)|🔌 基礎設施層=網路與儲存的具體實作。箭頭=依賴方向,只能由上往下,下層不知道上層存在。

各層職責與理由

  1. UI 層:只負責畫,不含業務邏輯。iOS 用 SwiftUI/UIKit,Android 用 Jetpack Compose。
  2. 簡報層(MVVM):MVVM = Model-View-ViewModel,一種 UI 架構模式——View(畫面)只負責顯示,ViewModel 負責把 Model(資料)轉成「畫面要的狀態」並處理畫面邏輯。選 MVVM 的理由:
    • 行情是持續的資料流,MVVM 搭配響應式框架(Combine / RxSwift / Kotlin Flow)最自然:資料流進來 → 轉換 → 綁定到 UI。
    • ViewModel 不依賴 UIKit,可以單元測試。
  3. 領域層:純業務規則(「限價單價格必須 > 0」「可用餘額 = 總額 − 凍結」)。不依賴框架,是最穩定、最值得測試的一層。小型 App 可省略,但交易邏輯複雜時這層讓規則只寫一次。
  4. 資料層(Repository 模式):ViewModel 只說「給我 BTC 行情流」,Repository 決定資料來自 WebSocket、REST 還是快取。換掉資料來源不動上面任何一層。
  5. 基礎設施層:WebSocket、HTTP、資料庫的具體實作,被 Repository 注入使用。

💡 這個分層對 Java 後端同學很親切:相當於 Controller → Service → Repository → DAO 的行動端版本,思想完全一樣——依賴抽象、單向依賴、每層只做一件事。

3. 核心難題一:即時行情資料流

交易所 App 架構的靈魂。設計重點:

圖例:實線箭頭=資料推送方向|虛線箭頭=觀察/綁定(響應式)|Note=關鍵策略說明。

面試要講出來的四個決策

  1. WebSocket 而非輪詢:行情高頻更新,HTTP 輪詢(polling,每隔幾秒問一次「有新資料嗎」)延遲高又浪費;WebSocket 是一條保持開著的長連線,由伺服器主動推資料下來。REST API 則指一般的「一問一答」HTTP 請求,本章用它拉歷史資料與快照。
  2. 節流(throttle)與合併:伺服器一秒推几十次,UI 不需要也畫不動。每 100~250ms 合併一次、同交易對只取最新值,UI 更新頻率和資料到達頻率解耦。
  3. 單一真相來源(Single Source of Truth):所有行情進同一個 Store,各頁面訂閱它。避免「列表頁和 K 線頁價格不同步」這種災難。
  4. 斷線重連策略:指數退避(exponential backoff,重試間隔 1s→2s→4s… 翻倍拉長)——如果所有斷線的 App 都每秒狂敲,伺服器剛復活就被打掛(雪崩);重連成功後先用 REST 拉一次快照補上漏掉的資料,再繼續吃增量推送(不然掛單簿會是錯的)。

K 線圖(可銜接自身的圖表實作經驗)

  • 歷史資料 REST 分頁載入 + 最新一根用 WebSocket 即時更新。
  • 渲染:資料量大時用繪圖層(Core Graphics / 自繪 Canvas)而非堆 View;只重繪可見範圍。
  • 手勢(縮放/平移)在 UI 層處理,資料視窗(可見的 N 根)由 ViewModel 計算。

4. 核心難題二:下單流程的正確性

使用者按下「買入」
  → 本地驗證(格式、餘額、最小單位)——快速擋掉明顯錯誤
  → 二次確認畫面(金額大時)
  → 送出(帶客戶端產生的唯一 requestId)
  → 等待伺服器回應
      ├─ 成功:顯示「已送出」,狀態以後續推送為準
      ├─ 失敗:顯示原因(餘額不足/價格偏離…)
      └─ 逾時:顯示「狀態未知」,用 requestId 向伺服器查詢,❌ 絕不自動重送

關鍵觀念(面試加分點):

  • 冪等性(idempotency):下單請求帶唯一 requestId,網路逾時重試也不會重複成交。這是金融 App 和一般 App 最大的差別之一。
  • 狀態以伺服器為準:本地只做「樂觀顯示」(optimistic UI:先假設會成功、畫面先顯示「送出中」,讓操作感覺即時),但訂單真正的狀態(已掛出/部分成交/全部成交)永遠聽伺服器推送,客戶端不自己推算。
  • 金額不用浮點數:iOS 用 Decimal/NSDecimalNumber,Android 用 BigDecimal,傳輸用字串。和 Java 章講的同一個理由。

5. 核心難題三:安全設計

面向 做法
認證 OAuth2(業界標準的授權流程)/ JWT(JSON Web Token,簽過章的登入憑證,伺服器可驗真偽):access token 短效 + refresh token 輪替
Token 保存 iOS Keychain / Android Keystore(系統提供的加密保險箱),絕不放 UserDefaults/SharedPreferences 明文
敏感操作 下單、提幣前再驗證:生物辨識(FaceID/指紋)或交易密碼
傳輸 全程 TLS(Transport Layer Security,HTTPS 底下的加密層)+ 憑證固定(certificate pinning):App 內寫死信任的伺服器憑證,防中間人攻擊
裝置風險 越獄/root 偵測、防截圖(資產頁)、App 切到背景時蓋遮罩
提幣 白名單地址、2FA(Two-Factor Authentication,二階段驗證:密碼之外再加一道,如簡訊或驗證器 App)、風控延遲——多半由後端主導,App 配合流程

6. 模組化與團隊協作

App 規模大了之後,單一專案會編譯慢、多人互相踩。依功能切模組:

圖例:方框=一個獨立編譯的模組|箭頭=依賴方向。規則:功能模組彼此不相依(透過介面/路由溝通),都只依賴核心模組;主模組負責組裝。

好處:編譯快(只編改到的模組)、權責清楚(行情團隊不會改壞交易模組)、可獨立測試。

7. 技術選型速答(面試快問快答用)

問題 建議回答
原生還是跨平台? 交易所核心 App 用原生:即時行情的效能、安全要求(Keychain/生物辨識)、圖表手感都是原生強項。行銷活動頁可用 WebView 混合。
iOS 用什麼 UI? 新功能 SwiftUI,但 K 線這種高效能自繪可能用 UIKit + Core Graphics;舊碼有 Objective-C 要能共存。
響應式框架? iOS:Combine(或既有專案的 RxSwift);Android:Kotlin Coroutines + Flow。理由:行情本質是資料流。
本地要存什麼? 使用者偏好、自選清單、K 線快取。餘額與訂單不做長期快取,顯示前一律刷新——寧可慢也不能錯。
怎麼測試? 領域層與 ViewModel 單元測試(注入假 Repository);WebSocket 用可重播的假資料源;UI 做關鍵路徑的 UI test(下單流程)。
監控? Crash 回報(Crashlytics 類)、關鍵指標埋點(下單成功率、WebSocket 斷線率、行情延遲)。

8. 一分鐘總結版(背起來)

「我會採用分層架構 + MVVM:UI、簡報、領域、資料、基礎設施五層,單向依賴。 行情走 WebSocket 單一資料流,經過節流合併進入單一真相來源 Store,各頁面響應式訂閱;斷線用指數退避重連、重連後先拉 REST 快照。 下單重視正確性:金額用 Decimal、請求帶冪等 ID、狀態以伺服器推送為準。 安全上 Token 進 Keychain、TLS 加憑證固定、敏感操作二次驗證。 規模化後依功能模組化,功能模組互不相依、共用核心模組。」

9. 練習題

✏️ 練習 1:使用者反映「行情列表很卡」,你會從哪些方向排查與優化?(點擊看參考答案)

依資料流一路查: 1. 更新頻率:有沒有節流?是不是每個 tick 都 reload 整個列表?→ 改成 100~250ms 合併 + 只更新變動的列(diff)。 2. 主執行緒:JSON 解析、數字格式化是否在主執行緒做?→ 移到背景,只有「套用到 UI」在主執行緒。 3. Cell 成本:cell 裡有沒有每次都重建 formatter、做複雜排版?→ 重用、預先計算。 4. 過度繪製:價格閃爍動畫是否觸發整列重繪?→ 只動需要的子視圖。 5. 量測:用 Instruments(Time Profiler)找真正的熱點,不要瞎猜。

✏️ 練習 2:App 在電梯裡斷線 30 秒後恢復,期間使用者的掛單已部分成交。畫面要怎麼回到正確狀態?(點擊看參考答案)
  1. WebSocket 偵測斷線 → 進入重連(指數退避),UI 顯示「連線中」狀態(誠實告知,避免使用者以為價格是最新的)。
  2. 重連成功後不能只繼續聽增量推送(中間漏掉的事件拿不回來): - 用 REST 拉快照:最新行情、該使用者的未成交訂單與餘額。 - 用快照覆蓋本地 Store(單一真相來源的好處:只要更新一處)。
  3. 快照套用後,再開始處理新的增量推送(注意順序:先快照、後增量,或用序號比對丟棄舊事件)。
  4. 部分成交的掛單由快照帶回正確狀態,UI 自動反映——因為所有頁面都訂閱同一個 Store,不需要逐頁修。
✏️ 練習 3:PM(產品經理)想在資產頁加「總資產折合日圓」的即時數字,需要所有幣種餘額 × 即時匯率。這個計算該放哪一層?為什麼?(點擊看參考答案)

放領域層(或由 ViewModel 呼叫的 UseCase): - 這是業務規則(總資產 = Σ 餘額 × 對應匯率),不是畫面邏輯,也不是資料存取。 - 放領域層可以單元測試(餵假餘額與假匯率,驗證加總與精度)。 - 資料來源是兩條流(餘額 + 行情)的合併:在 ViewModel 用響應式 combine 兩個 Store 的流,丟給 UseCase 計算,輸出一個「顯示用字串」給 UI。 - 精度注意:用 Decimal 累加,最後才格式化;不要在 UI 層拿 double 亂加。
