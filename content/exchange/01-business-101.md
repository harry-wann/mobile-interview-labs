## 重點講解

這個單元回答六個面試常見問題：

1. 販売所和取引所差在哪？使用者到底是在跟誰買賣？
2. 訂單簿是什麼？「約定」「部分約定」「maker／taker」是什麼意思？
3. 成行、指値、逆指値這三種基本的下單方式有什麼差別？
4. OCO、IFD、IFDOCO 這些組合單是怎麼運作的？
5. 槓桿交易的証拠金、維持率、追証、ロスカット是什麼？
6. 積立、貸暗号資産、入出金和入出庫（含トラベルルール）是什麼？

日本交易所的業務名詞，這個單元一律保留日文原文，後面附上中文意思。「暗号資産」是日本法規對加密貨幣的正式稱呼，交易所的畫面和公告都用這個詞。範例裡的價格都是為了說明而編的數字，不是實際行情。

### 1. 販売所和取引所差在哪？使用者到底是在跟誰買賣？

**販売所（はんばいじょ，店頭交易）是跟交易所自己買賣，價格由交易所報給你；取引所（とりひきじょ，板取引）是跟其他使用者買賣，價格由大家掛出來的單決定。** 兩者的成本藏在不同的地方：販売所的成本主要在買價和賣價的差額（spread），取引所的成本是手續費，加上大量下單時的滑價。

先用販売所走一遍。畫面上會同時出現兩個價格（價格都是 1 BTC 的價格）：

- 購入價格 10,100,000 円：你買 1 BTC（Bitcoin，比特幣）要付的價格。
- 売却價格 9,900,000 円：你賣 1 BTC 能拿到的價格。

如果你買進 1 BTC 之後馬上賣掉，付出 10,100,000 円，拿回 9,900,000 円，什麼都沒做就少了 200,000 円（約 2%）。這個差額叫 spread（買賣價差）。就算畫面上寫「手續費 0 円」，這 200,000 円還是使用者實際付出的成本。這就像機場的換匯櫃檯：櫃檯自己報價，買進和賣出的匯率不一樣，差價就是櫃檯的收入。

再看取引所。同一個時間點，取引所的訂單簿上，最低的賣價可能是 10,001,000 円，最高的買價是 10,000,000 円，兩邊只差 1,000 円。使用者買賣時，是跟板上其他人掛的單成交，另外要付 maker／taker 手續費（下一個問題會說明這兩個詞）。如果一次買很多，可能一路吃到好幾個價位，平均成交價會比一開始看到的差，這叫滑價（slippage，實際成交價和預期價格的差距），第 3 個問題會算給你看。

| | 販売所（店頭） | 取引所（板取引） |
|---|---|---|
| 跟誰買賣 | 交易所自己，價格由交易所報價 | 其他使用者，價格由訂單簿決定 |
| 畫面上看到 | 購入和売却**兩個價格** | 訂單簿（板）、最新成交價、K 線（一段時間內的開盤、最高、最低、收盤價） |
| 成本 | 主要是 spread，手續費可能標示為 0 | maker／taker 手續費，加上滑價 |
| 下單流程 | 通常是「報價、確認、成交」，報價有有效秒數 | 成行、指値、逆指値等，進入訂單簿排隊 |
| 一定買得到嗎 | 交易所保證可以成交（在額度內） | 取決於板上有多少單可以成交，可能只成交一部分 |

日本的加密資產交易所通常兩者都有，另外還有槓桿交易。這套交易所 API（Application Programming Interface，程式介面；格式與 Huobi 相容）有獨立的販売所 WebSocket（`wss://api.example-exchange.com/retail/ws`），和一般的行情 WebSocket（`/ws`）分開，反映出兩者的資料來源本來就不同。WebSocket 是一種讓伺服器可以持續主動推送資料給 App 的連線方式。取引所的行情會分成 depth（板的深度，每個價位掛了多少量）、bbo（best bid and offer，最佳買賣價）、trade（成交明細）這幾種資料，而且是 gzip 壓縮的二進位資料、需要定時回應心跳（ping／pong），這些連線細節見 WebSocket 協定單元。現貨手續費方面，有些業者會標示為免費；就算如此，販売所的實際成本仍然在 spread 裡。

**App 端要注意三件事：**

- 販売所頁面的購入價格和売却價格要同時顯示，不能顛倒，也不能只顯示其中一個。
- 一般的報價式交易，報價只在幾秒內有效，所以要做倒數；過期後要重新取得報價，不能用過期的價格送單。有效秒數與機制各家不同，面試時用「一般的做法」來描述。
- 使用者按下確認時，如果伺服器的價格已經和畫面上不同，要明確提示「価格が変動しました」（價格變動了）並請使用者重新確認。

> [!TIP]
> 面試時可以這樣說：「販売所是跟交易所自己買賣，成本在買賣價差；取引所是使用者之間的板取引，成本是手續費加滑價。被問哪個比較好，我不會選邊：新手要簡單、確定成交，用販売所；在意成本的人用取引所。App 的責任是把成本和風險講清楚。」

### 2. 訂單簿是什麼？「約定」「部分約定」「maker／taker」是什麼意思？

**訂單簿（日文叫「板」，いた）是一張列出所有人「想用什麼價格買或賣多少」的表。成交叫「約定」（やくじょう）。掛在板上等人來成交的單，那一方是 maker；直接吃掉板上既有的單，那一方是 taker。**

訂單簿分成兩邊：買單那邊叫 bid，賣單那邊叫 ask。排序規則是「價格優先、同價格時間優先」：買單出價高的排前面，賣單要價低的排前面，價格一樣就先掛的先成交。

```text
賣板（ask，想賣的人）           買板（bid，想買的人）
價格 10,010,000   數量 0.3 BTC    價格 9,990,000   數量 0.4 BTC
價格 10,000,000   數量 0.2 BTC    價格 9,980,000   數量 0.6 BTC
 ↑ 最低賣價                        ↑ 最高買價
```

現在走一遍 maker 和 taker。使用者送出一張**指値買單**（指定價格的買單，細節見第 3 個問題）：買 0.5 BTC，價格 10,005,000 円。

1. 板上最低的賣價是 10,000,000 円，比他願意出的 10,005,000 円還便宜，所以馬上成交：先吃掉 0.2 BTC。成交價是**板上的價格** 10,000,000 円，不是他的委託價。這一段是 taker（吃單）。
2. 次低的賣價 10,010,000 円比他的出價高，吃不到。剩下的 0.3 BTC 以 10,005,000 円掛在買板上，成為 maker（掛單）。
3. 這張單現在的狀態是 PartiallyFilled（部分成交），App 要顯示「已成交 0.2／剩餘 0.3」。訂單常見的狀態有 New（已受理，等待成交）、PartiallyFilled（部分成交）、Filled（全部成交）、Cancelled（已取消）。
4. 之後有人賣出 0.3 BTC、價格不高於 10,005,000 円，這 0.3 BTC 就以 10,005,000 円成交（因為是掛在板上等人來吃，成交價是他自己掛的價）。整張單的平均成交價是 (0.2 × 10,000,000 + 0.3 × 10,005,000) ÷ 0.5 = 10,003,000 円。

**部分約定**（ぶぶんやくじょう，一張單只成交了一部分）是這個例子的核心。幾個必須處理的地方：

- App 要顯示「已成交數量／剩餘數量／平均成交價」，不能只顯示委託價。
- 取消這張單，只會取消還沒成交的 0.3 BTC，已經成交的 0.2 BTC 不會回復。
- 狀態要顯示 PartiallyFilled（部分成交），不能顯示成「已成交」。剩下的數量取消之後，才會釋放被鎖住的餘額。

如果使用者希望整張單都一定是 maker（因為 maker 手續費通常比 taker 低），要用 post-only 這類選項：它的意思是「只准掛單、不准吃單」，要是價格會吃到板上的單，這張單就不會送進板（各家的處理方式不同，多半是直接拒絕）。是否提供這個選項要看各家交易所。maker 和 taker 的手續費率也不一樣，費率以交易所的公告為準。

另外有一個不用準備的名詞：板寄せ（いたよせ），就是集合競價，先收一段時間的單，再用同一個價格一次撮合。加密貨幣交易所是連續撮合（撮合就是把買單和賣單配對起來；連續撮合是只要有配得上的單，就立刻成交），不會考這個。

> [!TIP]
> 面試時可以這樣說：「maker 是掛單等人來吃，taker 是吃掉板上既有的單。一張指値單如果價格已經跨過對手的最佳價，會先以板上的價格成交，剩下的才進板成為 maker，所以一張單可能同時有兩種身分，也會變成部分成交。App 要顯示已成交、剩餘和平均成交價。」

### 3. 成行、指値、逆指値這三種基本的下單方式有什麼差別？

**成行（なりゆき，市價單）是不指定價格，立刻吃板直到成交；指値（さしね，限價單）是自己指定價格，可能不成交；逆指値（ぎゃくさしね，停損單）是價格到達某個點才啟動的條件單。**

先用成行說明滑價。假設賣板有三層：

| 價格 | 數量 |
|---|---|
| 10,000,000 円 | 0.2 BTC |
| 10,010,000 円 | 0.3 BTC |
| 10,030,000 円 | 0.5 BTC |

使用者下**成行買單** 0.6 BTC。系統會從最便宜的開始吃：

- 0.2 BTC × 10,000,000 = 2,000,000 円
- 0.3 BTC × 10,010,000 = 3,003,000 円
- 0.1 BTC × 10,030,000 = 1,003,000 円

總共花 6,006,000 円，平均成交價 10,010,000 円。如果全部都用最低賣價買，只要 6,000,000 円，多花的 6,000 円就是滑價。板上的單越少，滑價越大。所以成行單送出前，App 應該用深度資料（每個價位掛了多少量）預估平均成交價，偏離過大就警告使用者；最後的結果一律以成交回報為準。

```swift
import Foundation

func D(_ s: String) -> Decimal { Decimal(string: s)! }

struct Level { let price: Decimal; var qty: Decimal }

// 賣板，由低價排到高價
var asks = [
    Level(price: D("10000000"), qty: D("0.2")),
    Level(price: D("10010000"), qty: D("0.3")),
    Level(price: D("10030000"), qty: D("0.5")),
]

var remaining = D("0.6")        // 還想買多少
var cost = Decimal(0)           // 目前花了多少日圓
for i in asks.indices where remaining > 0 {
    let take = min(remaining, asks[i].qty)   // 這一層最多吃多少
    cost += take * asks[i].price
    asks[i].qty -= take
    remaining -= take
}
let filled = D("0.6") - remaining
print(filled, cost, cost / filled)
// 輸出：0.6 6006000 10010000
```

再看指値。同樣的賣板，使用者下**指値買單** 0.6 BTC，價格 10,010,000 円。價格超過 10,010,000 円的那一層不肯買，所以只吃前兩層：0.2 × 10,000,000 + 0.3 × 10,010,000 = 5,003,000 円，成交 0.5 BTC，平均成交價 10,006,000 円。剩下的 0.1 BTC 以 10,010,000 円掛在買板（之後成交算 maker）。指値單的好處是價格有上限，代價是不保證全部成交。指値的價格要對齊 tick size（價格的最小跳動單位，例如只能以 10 円為一格，細節見精度與金額單元）。

最後是逆指値，這個最容易搞混。假設使用者持有 BTC，現價 10,000,000 円，想在跌到 9,500,000 円時停損賣出。

- 正確做法：下**賣出逆指値**，觸發價 9,500,000 円。價格在觸發價之前，這張單不會進板、也不會成交；價格跌到 9,500,000 円，系統才送出實際的賣單（一般是成行賣單，有些業者讓你另外指定觸發後的委託價）。
- 錯誤做法一：下**賣出指値**，價格 9,500,000 円。現價是 10,000,000 円，買方願意出的價格比你的賣價高，這張單會**立刻成交**，完全不是停損。
- 錯誤做法二：賣出逆指値的觸發價設成 10,500,000 円。賣出的觸發價要低於現價（買入的逆指値則要高於現價，例如想在突破 10,500,000 円時追買），放錯邊會立刻觸發，或被伺服器拒絕。

要注意的是：觸發之後送出的是成行單時，實際成交價可能比 9,500,000 円更差，因為價格暴跌時板上的單會很薄。另外，「用哪個價格判斷有沒有到觸發價」（最新成交價、買價或賣價）各家不同，要查該交易所的規格。

| 種類 | 白話 | App 端要注意 |
|---|---|---|
| 成行（市價單） | 不指定價格，吃板直到成交 | 預估平均成交價和滑價，偏離過大要警告 |
| 指値（限價單） | 指定價格，可能不成交 | 價格對齊 tick size；價格跨過對手價時等於立即成交 |
| 逆指値（停損單） | 價格到達**觸發價**後才送出實際委託 | 分清楚「觸發價」和「委託價」兩個欄位；驗證方向；觸發由伺服器判定，App 關掉也會生效 |

各家交易所實際提供哪幾種注文（下單類型）不一定相同。面試時用「一般的做法」描述，不要說成某一家的規格。

> [!TIP]
> 面試時可以這樣說：「成行是不管價格、立刻成交，板薄的時候會有滑價，所以我會用深度資料預估平均成交價並警告使用者。逆指値要分清楚觸發價和委託價，觸發一定要由伺服器判斷，不能由 App 自己盯價格再下單，因為 App 進背景或斷線就不會觸發。」

### 4. OCO、IFD、IFDOCO 這些組合單是怎麼運作的？

**OCO、IFD、IFDOCO 都是把兩張或三張單綁在一起的組合單：OCO 是二選一，一張成交另一張就自動取消；IFD 是第一張成交了，才送出第二張；IFDOCO 是先進場，進場成交後自動掛上停利加停損。** 它們都是伺服器端的狀態機（state machine，把流程拆成幾個狀態，並規定每個狀態遇到什麼事件會換到哪個狀態），App 負責輸入、顯示和取消。

三個縮寫的來源：OCO 是 One Cancels the Other（一個成交，取消另一個）；IFD 是 If Done（如果完成了，就……）；IFDOCO 是 IFD 加 OCO。

用同一個例子走一遍。使用者想在 9,800,000 円買 0.1 BTC，買到之後，希望賺到 10,300,000 円就賣掉（停利），或跌到 9,500,000 円就認賠賣掉（停損）。

- **OCO**：使用者已經持有 BTC，同時掛兩張賣單：賣出指値 10,300,000 円（停利）加賣出逆指値、觸發價 9,500,000 円（停損）。價格先漲到 10,300,000 円，賣出指値成交，另一張逆指値自動取消；反過來也是一樣。
- **IFD**：先掛買入指値 9,800,000 円。這張單成交之前，第二張賣單只是待機中，還沒有送到訂單簿。買單成交之後，系統才自動送出賣出指値 10,300,000 円。
- **IFDOCO**：IFD 的第二段是 OCO。買入指値 9,800,000 円成交後，系統自動送出一組 OCO：賣出指値 10,300,000 円加賣出逆指値、觸發價 9,500,000 円。使用者一次設定好進場、停利、停損，不用盯盤。

App 端最容易出問題的是狀態：待機中的單要不要預先鎖住餘額，要看規格；OCO 取消其中一張時，另一張也要一起顯示出來；IFDOCO 有三張單，彼此的關聯要用資料結構表達，不要用字串拼。下面是一個示意（一般做法的寫法，不是某一家交易所的規格）：

```swift
import Foundation

enum Side { case buy, sell }

enum OrderKind {
    case market                       // 成行
    case limit(price: Decimal)        // 指値
    case stop(trigger: Decimal)       // 逆指値：到了觸發價才送出實際委託
}

struct SingleOrder {
    let side: Side
    let kind: OrderKind
    let quantity: Decimal
}

// 用 enum 表達「這幾張單是什麼關係」，不要用字串拼
enum OrderGroup {
    case single(SingleOrder)
    case oco(SingleOrder, SingleOrder)                              // 二選一
    case ifd(first: SingleOrder, then: SingleOrder)                // 第一張成交後才送出第二張
    case ifdoco(first: SingleOrder, takeProfit: SingleOrder, stopLoss: SingleOrder)
}

let qty = Decimal(string: "0.1")!
let group = OrderGroup.ifdoco(
    first: SingleOrder(side: .buy, kind: .limit(price: 9_800_000), quantity: qty),         // 進場
    takeProfit: SingleOrder(side: .sell, kind: .limit(price: 10_300_000), quantity: qty),  // 停利
    stopLoss: SingleOrder(side: .sell, kind: .stop(trigger: 9_500_000), quantity: qty)     // 停損
)
if case .ifdoco(let first, _, _) = group, case .limit(let price) = first.kind {
    print("進場價格", price)
}
// 輸出：進場價格 9800000
```

各家交易所有沒有提供 OCO、IFD、IFDOCO、提供哪幾種，要看該家的規格。

> [!TIP]
> 面試時可以這樣說：「OCO 是二選一，IFD 是第一張成交才送出第二張，IFDOCO 是進場之後自動掛停利和停損。這些都是伺服器端的狀態機，App 負責輸入驗證、顯示每一張單的狀態和取消。我會用資料結構表達這幾張單的關聯，不會用字串拼。」

### 5. 槓桿交易的証拠金、維持率、追証、ロスカット是什麼？

**槓桿（レバレッジ）是只放一部分錢當擔保，就能做更大金額的買賣，賺賠都會被放大。擔保金的比例掉得太低，系統就會要求補錢（追証），再低就直接強制平倉（ロスカット）。** 所以 App 要即時、清楚地顯示風險。日本對個人客戶的槓桿上限是 2 倍（整理自一般的法規知識，面試前可以再核對最新規定）。

名詞先對齊：

- **証拠金**（しょうこきん，保證金）：開倉時放進去的擔保金。
- **建玉**（たてぎょく，持倉部位）：已經買進、還沒賣掉的部位。
- **評価損益**（ひょうかそんえき）：以目前價格算出來、帳面上的賺賠，還沒有真的賣掉。
- **有効証拠金**：証拠金加上評価損益，也就是現在真正剩下多少擔保。
- **必要証拠金**：維持目前的建玉所需要的最低擔保金。
- **維持率**：有効証拠金 ÷ 必要証拠金。這是一般的定義，各家業者實際的算法可能不同。數字越低越危險。
- **追証**（おいしょう，追加証拠金）：維持率掉到警戒線時，要求使用者補保證金。
- **ロスカット**：維持率再掉到門檻以下，系統**強制平倉**（強制幫你賣掉，把部位了結），避免虧損繼續擴大。

用數字走一遍。使用者放 1,000,000 円的証拠金，用 1.6 倍的槓桿買進 1,600,000 円的 BTC（建玉 1,600,000 円）。為了好懂，假設必要証拠金是建玉的一半，也就是 800,000 円，而且不隨價格變動（實際上很多業者會用即時價格重算）。再假設追証的警戒線是維持率 100%、ロスカット的門檻是 50%。這兩個數字是為了說明假設的，不是某一家交易所的規則。

| BTC 價格變化 | 評価損益 | 有効証拠金 | 維持率 | 狀態 |
|---|---|---|---|---|
| 沒變 | 0 円 | 1,000,000 円 | 125% | 正常 |
| 下跌 10% | −160,000 円 | 840,000 円 | 105% | 正常，但已經很接近警戒線 |
| 下跌 15% | −240,000 円 | 760,000 円 | 95% | 低於 100%，要補保證金（追証） |
| 下跌 40% | −640,000 円 | 360,000 円 | 45% | 低於 50%，被強制平倉（ロスカット） |

幾個重點：

- 下跌 10%，損失是 160,000 円，佔証拠金的 16%。如果沒有槓桿，用 1,000,000 円直接買，下跌 10% 只虧 100,000 円（10%）。這就是「賺賠都放大」。
- 維持率會跟著價格一直變動，所以要以伺服器算出來的數字為準。
- 追証的有無、門檻的數字、ロスカット的水準，每家業者自己訂，面試時不要背別家的數字。
- 槓桿交易持倉期間，業者可能收取資金調整額（持倉期間產生的費用或收付）。名稱和計算方式各家不同。
- 槓桿商品的交易對各家不同，常見的是 BTC/JPY（用日圓買賣 BTC 的交易對）。

**App 端要注意：**

- 倍率上限（2 倍）要在輸入畫面（UI，User Interface，使用者介面）和送單前都擋住，伺服器仍會再驗證一次。
- 畫面要即時顯示維持率、評価損益、ロスカット的價格，以伺服器推送的值為準。不要在 App 用最後一次的價格自己推算維持率，再用它決定使用者能不能加碼，因為過期的價格會讓使用者在已經危險的時候看到安全的數字。
- 強制平倉對使用者影響最大，要用推播（push notification）加畫面通知，歷史紀錄也要顯示平倉價格和損益。
- 損益可能是負數，捨入方向的差異見精度與金額單元。

> [!TIP]
> 面試時可以這樣說：「槓桿是用少量保證金做大的部位，賺賠都放大。維持率是有効証拠金除以必要証拠金，掉到警戒線要追証，掉到門檻就ロスカット強制平倉。日本個人客戶上限是 2 倍。App 端我會在輸入時擋倍率，維持率和平倉價格以伺服器推送的值為準，被強制平倉要通知使用者。」

### 6. 積立、貸暗号資産、入出金和入出庫（含トラベルルール）是什麼？

**積立是定期自動買入；貸暗号資産是把幣借給交易所賺利息；入出金是日圓進出，入出庫是加密貨幣進出。其中「出庫」最敏感，流程最長，因為還要符合トラベルルール。**

- **積立**（つみたて，定期定額買入）：常見的設定是 1,000 円起。技術上，排程應該放在伺服器端，App 只負責設定、顯示下次扣款日和歷史。
- **貸暗号資産**（かしあんごうしさん，借幣生息）：把持有的幣借給交易所並收利息。多數業者有鎖定期間，期間內不能賣出或出庫，實際條件各家不同。App 要把期間和限制講清楚。
- **日圓入出金**（にゅうしゅっきん）：銀行轉帳。多數業者提供「クイック入金」（快速入金）這類即時入金服務，手續費各家不同。
- **暗号資産入出庫**（にゅうしゅっこ）：入庫＝把幣轉進來（充幣），出庫＝把幣轉出去（提幣）。

**トラベルルール**（旅行規則，Travel Rule）是 2023 年 6 月起的規定：為了防制洗錢，加密貨幣從一間交易所轉到另一間時，兩邊要互相交換「誰送、誰收」的資料。對 App 的影響是出庫流程多了幾步。假設使用者要提 0.1 BTC 到另一間交易所，流程大致如下（一般做法的描述，實際畫面順序以各家 App 為準）：

1. **登錄出庫地址**：選擇網路（同一種幣可能有好幾條區塊鏈可以轉帳，選錯很難挽回），並依トラベルルール申告對方是其他交易所還是自己的錢包。
2. **地址審核**：地址要經過審核（承認）才能使用。這需要一段時間，不是馬上有結果，所以要畫出「審査中（審核中）、承認（通過）、否認（不通過）」的狀態，並用推播通知結果，不然使用者會以為卡住了。多數業者的出庫地址都有類似的審查流程。
3. **選擇已通過審核的地址**，畫面顯示該網路的手續費和最小出庫量。
4. **輸入數量**：App 先預檢可用餘額、最小量、數量精度，並顯示確認畫面。
5. **二階段驗證（2FA，Two-Factor Authentication）或生物辨識確認後送出**，狀態依序是審査中、處理中、完了（完成）。

**eKYC** 是 electronic Know Your Customer 的縮寫，意思是在手機上完成身分確認。日本的加密資產交易所 App 通常支援掃描マイナンバーカード（個人編號卡）。卡片晶片裡有一張電子證明書，叫 JPKI（公的個人認証，Japanese Public Key Infrastructure），App 用 NFC（Near Field Communication，近距離無線通訊）讀卡就能證明是本人，這是法規允許的方式裡最可靠的一種。App 端要設計失敗路徑，例如卡片讀取失敗、裝置不支援 NFC、逾時，以及改走其他驗證方式的入口。細節見 eKYC 與合規單元。

最後，整理日本的加密資產交易所 App 通常有的功能：數十種幣種、販売所＋取引所＋槓桿、積立、マイナンバーカード eKYC、價格提醒、損益分析、貸暗号資産、日文／簡中／繁中／英文等多種語言。

> [!TIP]
> 面試時可以這樣說：「出庫是最敏感的流程。因為トラベルルール，地址登錄要多一步申告，地址還要審核，所以出庫是多步驟、非同步的流程。我會把它做成狀態機，畫出審核中、通過、不通過，並用推播通知結果，錯誤訊息要具體，例如網路選錯、地址格式錯誤。」

### 演練 1：畫面寫的價格和實際成交價不同（第 1 題）

**檔案**：`L01_QuoteExpiry.swift`（iOS）、`L01_QuoteExpiry.kt`（Android）

**情境**：販売所的買進畫面顯示「購入價格 10,100,000 円、売却價格 9,900,000 円」，報價 5 秒內有效。使用者看了 7 秒才按確認，這段時間交易所的報價已經漲到 10,160,000 円。演練用一個假的報價櫃檯，時間用毫秒數傳進去，不用真的等。

**怎麼寫**

1. **Bug 版**：`confirm` 呼叫櫃檯的 `buy` 時只送數量，報價編號傳 `nil`（Android 是 `null`）。
2. **修正版**：呼叫 `buy` 時帶上使用者看到的報價編號 `quote.id`。報價過期時，櫃檯不成交，改回傳新的報價，演練流程會顯示「価格が変動しました」，使用者看過新價格再按一次確認。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 「成交價 10160000，畫面上顯示的是 10100000，多付 60000 円」，沒有任何提示 |
| 修正版 | 「価格が変動しました：新的購入價格 10160000（原本 10100000），沒有成交」，使用者重新確認後才以 10160000 成交 |

**為什麼**：販売所是跟交易所自己買賣，價格由交易所報價，所以報價有有效時間。按確認時如果不告訴櫃檯「我看到的是哪一個報價」，櫃檯只能用當下的價格成交，使用者就在不知情的情況下多付了錢。帶上報價編號之後，櫃檯能判斷這個報價是不是還有效；過期就退回新報價，由使用者決定要不要接受。畫面第一行的價差（購入價格減売却價格，200,000 円）才是販売所真正的成本，就算手續費寫 0 円也一樣。有效秒數與機制各家不同，面試時用「一般的做法」來描述。

### 演練 2：成交一半的單顯示「已成交」，取消時多算了錢（第 2 題）

**檔案**：`L02_PartialFill.swift`（iOS）、`L02_PartialFill.kt`（Android）

**情境**：使用者送出指値買單：買 0.5 BTC，委託價 10,005,000 円。賣板最低的 0.2 BTC 賣 10,000,000 円，所以立刻成交 0.2 BTC，剩下的 0.3 BTC 以 10,005,000 円掛在買板上。使用者看了一下，按「取消」。這就是上面「部分約定」的例子。

**怎麼寫**

1. **Bug 版**：iOS 的 `status(of:)`（Android 的 `status`）只要 `filled > 0` 就回傳 `.filled`（Android 是 `FILLED`）；`release(of:)`（Android 的 `release`）用整張單的 `qty × price` 算取消後釋放的金額。
2. **修正版**：成交量等於委託量才是 `.filled`，有成交但還沒滿是 `.partiallyFilled`（Android 是 `PARTIALLY_FILLED`）；釋放的金額只算剩餘數量 `(qty − filled) × price`。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 「狀態：Filled，已成交 0.2／剩餘 0.3」「取消後釋放 5002500 円」（把已經成交用掉的 0.2 BTC 也算進去） |
| 修正版 | 「狀態：PartiallyFilled，已成交 0.2／剩餘 0.3」「取消後釋放 3001500 円」（只有剩餘的 0.3 × 10,005,000） |

**為什麼**：一張單可以只成交一部分，狀態要顯示 PartiallyFilled，不能顯示成「已成交」。取消只會取消還沒成交的剩餘數量，已經成交的 0.2 BTC 不會回復，錢也已經花掉了，所以釋放的金額只能算剩餘的部分。另外要注意：成交價是板上的 10,000,000 円，不是委託價 10,005,000 円，委託價只是願意付的上限。

### 演練 3：指値買單的手續費算少了（第 2 題）

**檔案**：`L03_MakerTakerFee.swift`（iOS）、`L03_MakerTakerFee.kt`（Android）

**情境**：和演練 2 同一張單。先吃掉賣板上的 0.2 BTC（成交價 10,000,000 円），這一筆是 taker；剩下的 0.3 BTC 掛在買板上，之後有人賣給他（成交價 10,005,000 円），這一筆是 maker。手續費率是演練的假設：maker 0.05%、taker 0.1%。

**怎麼寫**

1. **Bug 版**：`rate` 用「下單的種類」決定費率：`orderType` 是指値就回傳 `makerRate`，否則回傳 `takerRate`。
2. **修正版**：`rate` 看這一筆成交實際的角色 `fill.role`：maker 回傳 `makerRate`，taker 回傳 `takerRate`。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 兩筆都用 maker 費率，手續費 1000 加 1500.75，「手續費合計 2500.75 円」 |
| 修正版 | 吃板的 0.2 BTC 手續費 2000，掛單的 0.3 BTC 手續費 1500.75，「手續費合計 3500.75 円」 |

**為什麼**：maker 和 taker 是「這一筆成交」的角色，不是「這張單」的屬性。一張價格跨過對手最佳價的指値單，先以 taker 吃板，剩下的才成為 maker，所以同一張單會有兩種手續費率。如果以為「指値就是 maker」，手續費會算少；畫面上預估的手續費和實際扣款對不起來，使用者就會來問。費率以交易所的公告為準。

### 演練 4：成行買單預估的價格，看不出滑價（第 3 題）

**檔案**：`L04_MarketSlippage.swift`（iOS）、`L04_MarketSlippage.kt`（Android）

**情境**：使用者要用成行買 0.6 BTC。賣板有三層：10,000,000 円 0.2 BTC、10,010,000 円 0.3 BTC、10,030,000 円 0.5 BTC。下單前 App 要預估平均成交價，預估的滑價（平均成交價比最低賣價貴多少）超過 0.05% 就要警告使用者（0.05% 是演練的假設）。

**怎麼寫**

1. **Bug 版**：`estimateCost` 用「數量 × 最低賣價」估算。
2. **修正版**：從最便宜的價位開始一層一層吃：每層最多吃 `min(剩餘數量, 這一層的數量)`，花費加上「吃的數量 × 這一層的價格」，直到湊滿數量為止。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 預估花費 6000000 円、「預估滑價 0%」、「滑價在 0.05% 以內，不警告」，但「實際吃板花費 6006000 円，和預估差 6000 円」 |
| 修正版 | 預估花費 6006000 円、平均成交價 10010000、「預估滑價 0.1%」、「⚠︎ 滑價超過 0.05%，要警告使用者」，和實際吃板的結果差 0 円 |

**為什麼**：成行單會一路吃掉好幾個價位，第一層只有 0.2 BTC，後面的 0.4 BTC 要用更貴的價格買。用最低賣價乘以數量，等於假設板上有無限多的單，滑價被藏起來，使用者看不到警告。板越薄，差距越大。預估只是讓使用者在送出前看到風險，最後的結果一律以成交回報為準。

### 演練 5：想設停損，逆指値送出去卻立刻成交（第 3 題）

**檔案**：`L05_StopDirection.swift`（iOS）、`L05_StopDirection.kt`（Android）

**情境**：BTC 現價 10,000,000 円。演練依序試四張逆指値：賣出 9,500,000（正確）、賣出 10,500,000（放錯邊）、買入 10,500,000（正確）、買入 9,500,000（放錯邊）。App 在送出前要檢查方向；放行的單送到假伺服器，如果現價已經滿足觸發條件，伺服器會立刻觸發。

**怎麼寫**

1. **Bug 版**：`validate` 的方向寫反：賣出要求觸發價「高於」現價，買入要求「低於」現價；符合就回傳 `nil`（Android 是 `null`），不符合回傳原因文字。
2. **修正版**：賣出要求觸發價低於現價（跌到才賣），買入要求觸發價高於現價（漲到才買）。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 賣出 9500000、買入 10500000 被誤擋；賣出 10500000、買入 9500000 被放行，伺服器立刻以 10000000 成交，「正確的單被誤擋 2 張，放錯邊卻立刻觸發 2 張」 |
| 修正版 | 賣出 9500000、買入 10500000 進入待機，另外兩張在 App 端擋下，「正確的單被誤擋 0 張，放錯邊卻立刻觸發 0 張」 |

**為什麼**：逆指値的意思是價格到達觸發價才送出實際委託。賣出的觸發價放在現價上方，伺服器收到時條件已經滿足，單子會立刻成交，使用者以為設了停損，其實是直接賣掉了。觸發由伺服器判斷，App 進背景或斷線也會生效；App 的責任是在輸入時把方向擋住，不要自己盯價格再下單。

### 演練 6：停利成交了，停損單還在、又賣了一次（第 4 題）

**檔案**：`L06_OcoCancel.swift`（iOS）、`L06_OcoCancel.kt`（Android）

**情境**：使用者持有 0.1 BTC，掛了一組 OCO：賣出指値 10,300,000 円（停利）加賣出逆指値、觸發價 9,500,000 円（停損），各 0.1 BTC。價格依序變成 10,000,000、10,300,000、9,800,000、9,500,000：先漲到停利價，停利單成交，接著暴跌到停損價。這是組合單的狀態機，伺服器用它決定每一張單的狀態，App 用同一套規則顯示。

**怎麼寫**

1. **Bug 版**：`onFilled` 只把成交的那一張標成 filled，另一張維持 active。
2. **修正版**：成交的那一張標成 filled；另一張如果還是 active，改成 cancelled。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 停利成交後持倉 0；價格跌到 9500000 時停損單又被觸發，再賣 0.1 BTC，「最後狀態：停利 filled、停損 filled，持倉 -0.1 BTC」 |
| 修正版 | 停利成交時停損單改成 cancelled，價格跌到 9500000 什麼都不會發生，「最後狀態：停利 filled、停損 cancelled，持倉 0 BTC」 |

**為什麼**：OCO 的規則是二選一：其中一張成交，另一張要自動取消。沒有取消的話，已經了結的部位後面還會被另一張單再賣一次，賣掉根本沒有的 BTC。IFD（第一張成交才送出第二張）和 IFDOCO（IFD 的第二段是 OCO）也是同一類狀態機；App 要用資料結構表達這幾張單的關係，並顯示每一張單目前的狀態，取消其中一張時，另一張也要一起顯示出來。

### 演練 7：跌了 40%，維持率還顯示 125%（第 5 題）

**檔案**：`L07_MarginRatio.swift`（iOS）、`L07_MarginRatio.kt`（Android）

**情境**：和上面的表一樣：使用者放 1,000,000 円的証拠金，以 10,000,000 円買進 0.16 BTC（建玉 1,600,000 円），必要証拠金固定 800,000 円；維持率低於 100% 追証，低於 50% ロスカット（這些數字是演練的假設）。價格依序變成：不變、跌 10%、跌 15%、跌 40%。

**怎麼寫**

1. **Bug 版**：`effectiveMargin` 直接回傳放進去的証拠金 `deposit`，沒有加評価損益。
2. **修正版**：`effectiveMargin` 回傳 `deposit + pnl`（有効証拠金 = 証拠金 + 評価損益，虧損時 `pnl` 是負數）。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 四個價格的維持率都是 125%，狀態都是「正常」，「被強制平倉（ロスカット）的價格：沒有」 |
| 修正版 | 維持率依序 125%、105%（正常）、95%（追証）、45%（ロスカット），「被強制平倉（ロスカット）的價格：6000000」 |

**為什麼**：維持率是有効証拠金除以必要証拠金，有効証拠金一定要把帳面上的賺賠算進去。只看放進去的証拠金，價格跌多少都不會變，使用者在最危險的時候看到的是最安全的數字。實際的 App 畫面要用伺服器推送的維持率，不要在 App 用過期的價格自己推算；這個演練只是練算法。追証、ロスカット的門檻每家業者自己訂。

### 演練 8：出庫送出去才被退回，地址還在審核中（第 6 題）

**檔案**：`L08_WithdrawPrecheck.swift`（iOS）、`L08_WithdrawPrecheck.kt`（Android）

**情境**：使用者有 0.1 BTC 可用，網路手續費 0.0005 BTC。演練依序試六筆出庫：已承認的地址 0.05 BTC、已承認的地址 0.1 BTC（餘額不夠付手續費）、審査中的地址、否認的地址、沒有登錄過的地址、已承認的地址 0.5 BTC（超過餘額）。App 要在送出前先預檢，擋得住的不要送到假伺服器；假伺服器自己也會再驗證一次。

**怎麼寫**

1. **Bug 版**：`precheck` 只檢查地址有沒有登錄過，以及數量不超過可用餘額。
2. **修正版**：地址的狀態必須是承認（approved），而且「數量加手續費」不能超過可用餘額；不符合就回傳原因，不送出。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 審査中、否認的地址和 0.1 BTC 都放行，「送到伺服器的出庫 4 筆，被伺服器退回 3 筆」 |
| 修正版 | 只有第一筆送到伺服器，其餘五筆在 App 端就被擋下並說明原因，「送到伺服器的出庫 1 筆，被伺服器退回 0 筆」 |

**為什麼**：出庫因為トラベルルール，地址要先經過審核才能使用，審核需要一段時間；轉帳還要扣網路手續費，餘額要夠付「數量加手續費」。預檢擋得住的錯誤，就不用讓使用者送出之後等一段時間才被退回，原因也能講得更具體。預檢只是提早擋錯，最終一律以伺服器為準。

## 常見陷阱

- **把販売所說成「手續費免費所以比較便宜」。** 販売所的成本在 spread。面試官會用這個測你有沒有金融概念。
- **逆指値的觸發價和委託價搞混。** 觸發價只是條件，沒有觸發之前，這張單不會進板；是否預先鎖住餘額要看規格。
- **在 App 端自己監看價格，到了再下單，來模擬逆指値。** App 在背景或斷線就不會觸發。觸發必須由伺服器判斷。
- **部分約定之後直接把狀態顯示成「已成交」。** 正確的狀態是 PartiallyFilled，取消剩餘數量之後才會釋放餘額。
- **用過期的價格在 App 自己算維持率，再據此做決策。** 畫面上的維持率要用伺服器推送的值，App 自己推算會讓使用者在危險的時候看到安全的數字。
- **把別家的規格當成這家的。** 槓桿倍率上限以外的細節，例如追証、ロスカット的水準、注文種類、手續費，都要查，不確定就說「依該交易所的規格為準」。

## 面試官想聽到的

1. 能用自己的話講出販売所和取引所的差別：販売所是跟交易所自己買賣、成本在 spread、價格由交易所保證（在額度內）；取引所是使用者之間撮合、成本是手續費加滑價、可能只成交一部分。
2. 知道 maker／taker 和成行的滑價，並對應到 App 的預估成交價和警告。
3. 知道逆指値、OCO、IFD 是伺服器端的狀態機，App 只負責輸入驗證、顯示和取消。
4. 說得出槓桿 2 倍上限、証拠金、維持率、ロスカット，以及 UI 要怎麼做風險揭露和即時顯示維持率。
5. 理解入出庫和トラベルルール：出庫流程多了申告和審核，App 要做好狀態和錯誤訊息，不能因為使用者趕時間就跳過。
6. 進入新的業務領域時，有具體的學習方法：對照交易所的 API 文件和 App 的實際畫面，把業務規則對齊之後再設計 UI 狀態。

> [!FIELD]
> 在一個加密貨幣市場分析 App 裡，做過清算地圖（Liquidation）和鯨魚追蹤頁面，畫的是伺服器算好的資料；也做過即時行情（用 SSE，Server-Sent Events，也就是伺服器單向推送資料的 HTTP 串流；HTTP 是 HyperText Transfer Protocol，一般的網路請求方式）。清算地圖顯示的就是強制平倉的價位分布。在日本團隊裡全程以日文協作，參與規格制定與 code review 的經驗，讓讀日文的業務文件不成問題。
> 面試時可以這樣說：「我做過即時行情和清算資料的呈現，知道使用者對強制平倉的價位很敏感。到交易所的 App，我會先讀交易所的 API 文件和 App 的實際流程，把業務規則對齊之後，再設計 UI 的狀態。」
