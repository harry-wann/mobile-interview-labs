## 重點講解

這個單元回答五個問題：

1. 一題系統設計，45 分鐘要怎麼分配？
2. App 端的架構，通常分成哪幾層？
3. 交易所 App 的設計題，除了功能還要講哪些需求？
4. 怎麼用數字讓設計更有說服力？
5. 面試官在每個階段看的是什麼？

### 1. 45 分鐘要怎麼分配？

**結論：固定照「需求 → 介面 → 架構 → 深入 → 例外情況 → 品質」的順序走。** 面試官最先觀察的，就是你會不會一聽到題目就開始畫圖。

| 階段 | 時間 | 要講出什麼 |
|---|---|---|
| 1. 釐清需求 | 5 分 | 要做什麼、不做什麼；功能以外的需求（延遲、正確性、離線、安全）；規模（幾個交易對、多久更新一次、多少使用者） |
| 2. API 與資料模型 | 5 分 | 用 REST 還是 WebSocket、訊息長什麼樣子、主要的資料型別 |
| 3. 整體架構圖 | 10 分 | 資料從伺服器 → 網路層 → App 內的各層 → 畫面，怎麼一路流過去 |
| 4. 深入一到兩個元件 | 15 分 | 例如連線管理、訂單簿的資料合併、下單的狀態流程 |
| 5. 例外情況與取捨 | 5 分 | 斷線、App 進背景、資料有缺漏、收到重複的資料、錯誤、權限 |
| 6. 品質 | 5 分 | 效能、測試、監控、發布 |

第 1 階段特別重要。題目通常很模糊（例如「請設計我們的行情列表」），你要主動問清楚，並且把假設寫下來，例如「假設 40 個交易對、每個每秒更新 2 次」。之後的設計都以這些假設為基礎。

第 6 階段常常是區分資深與一般工程師的地方：講得出「上線後怎麼知道它是好的」（監控指標、crash 率、延遲），比多畫一個方塊更有說服力。

> [!TIP]
> 面試時可以這樣開場：「在開始設計之前，我想先確認幾件事：範圍、資料、即時性、規模和平台限制。確認完我會把假設寫下來，再畫資料怎麼流動。」

### 2. App 端的架構通常分成哪幾層？

**結論：從網路到畫面分成四層，資料單向往畫面流動；耗時的工作都在背景，主執行緒只負責把算好的結果畫出來。**

```text
┌──────────────┐   ┌───────────────┐   ┌───────────────┐   ┌──────────┐
│ 網路層        │ → │ 資料層         │ → │ 狀態層         │ → │ 畫面      │
│ REST / WS    │   │ Repository    │   │ ViewModel     │   │ SwiftUI /│
│ 連線管理      │   │ 記憶體/磁碟快取 │   │ （StateFlow / │   │ Compose  │
│ 驗證、重試    │   │ 合併、去重複    │   │  @Observable）│   │          │
└──────────────┘   └───────────────┘   └───────────────┘   └──────────┘
   背景執行緒：解壓縮、解析、合併、計算 ──────────────→ 主執行緒：只負責畫面
```

每一層的工作：

- **網路層**：管理 WebSocket 連線（連線、心跳、斷線重連）、REST 請求、加上驗證資訊、失敗重試。
- **資料層（Repository）**：把網路來的資料整理好、合併、去掉重複的，必要時存到快取。對上層來說，它是「資料唯一的來源」。
- **狀態層（ViewModel）**：把資料轉成畫面需要的狀態，例如「這一列要顯示的價格字串、漲跌顏色」。
- **畫面**：只讀取狀態並顯示，不自己去拿資料、也不自己改資料。

三個要講出來的設計原則：

1. **單一資料來源（single source of truth）**：同一份資料只存在一個地方（Repository 或 Store），畫面只讀它。這樣不會出現「首頁顯示的價格和詳細頁不一樣」。
2. **執行緒的分界**：解壓縮、JSON 解析、合併、計算都在背景執行緒；主執行緒只接收已經算好、可以直接顯示的狀態。主執行緒一忙，畫面就會卡頓。
3. **生命週期**：畫面離開時取消訂閱；App 進背景時要不要斷線；回到前景時怎麼把錯過的資料補回來。

> [!TIP]
> 面試時可以這樣說：「我會把 App 分成網路層、資料層、狀態層和畫面四層，資料單向往畫面流動。解析和合併都在背景執行緒，主執行緒只負責顯示算好的狀態。同一份資料只存在 Repository，畫面只讀它，避免不同畫面顯示不一樣的數字。」

### 3. 交易所 App 的設計題，除了功能還要講哪些需求？

功能以外的需求（面試常稱為「非功能需求」），交易所 App 一定要主動提：

| 需求 | 具體要講什麼 |
|---|---|
| 正確性 | 金額用 `Decimal`／`BigDecimal`，不用 `Double`；訂單狀態以伺服器為準；檢查訊息的序號有沒有跳號 |
| 即時性 | 行情延遲的目標（例如 500 毫秒內）；畫面更新頻率的上限（例如每秒最多 10 次） |
| 可靠性 | 斷線後自動重連（等待時間逐次加倍，再加一點隨機誤差）；下單帶 client order id 避免重複下單；離線時明確提示 |
| 安全性 | token 存在 Keychain／Keystore；生物辨識；憑證綁定（certificate pinning）；資產畫面防截圖 |
| 效能 | 主執行緒每一格畫面的時間預算（60Hz 約 16 毫秒、120Hz 約 8 毫秒）；記憶體上限；耗電 |
| 法規 | 風險說明；槓桿上限（日本是 2 倍）；出金時的トラベルルール（travel rule，轉帳要附上收款方資訊） |

不需要每一項都講很深，但要讓面試官知道你有想到。

> [!TIP]
> 面試時可以這樣說：「功能以外，交易所 App 我最在意的是正確性和可靠性：金額一律用 Decimal，訂單狀態以伺服器為準，斷線要能自動補回資料，下單要能安全重試。」

### 4. 怎麼用數字讓設計更有說服力？

簡單的估算，能讓「為什麼要這樣設計」變得具體。三個交易所題目常用的例子：

- **首頁行情列表**：40 個交易對，每個每秒更新 2 次，一秒就是 80 則訊息。如果每則訊息都直接更新畫面，一秒要重畫 80 次。改成在背景先把訊息合併成「每個交易對的最新價格」，每 100 毫秒更新一次畫面，就只剩每秒 10 次。這樣「收到訊息的頻率」和「畫面更新的頻率」就分開了，不會互相影響。
- **訂單簿**：每次推送完整的買賣各約 150 檔，背景解析和整理只要幾毫秒，**真正的瓶頸在畫面更新**。所以最佳化的重點是減少畫面重畫的範圍和次數。
- **K 線**：1 分鐘 K 線保留 2000 根，每根 6 個欄位、每個 8 bytes，大約 96KB，記憶體完全不是問題。問題在重畫的效能，以及如果圖表是 WebView，原生和 JavaScript 之間傳資料的成本。

估算不用精準，重點是**找出瓶頸在哪裡**，再把設計的力氣花在那裡。

> [!TIP]
> 面試時可以這樣說：「我先估一下：40 個交易對每秒 2 次就是 80 則訊息。瓶頸不在解析，而在畫面更新，所以我會在背景合併，每 100 毫秒更新一次畫面，主執行緒每秒只處理 10 次。」

### 5. 面試官在每個階段看的是什麼？

- **需求階段**：會不會主動問、會不會把假設寫下來。
- **架構階段**：資料怎麼流動、狀態放在哪裡、哪些在背景執行緒，講得清不清楚。只說「我會用 Clean Architecture」卻講不出資料怎麼流，是扣分的。
- **深入階段**：至少有一個元件講到實作的細節，例如狀態有哪幾種、怎麼轉換，用什麼資料結構。
- **取捨**：為什麼這樣選、代價是什麼、什麼情況下會改成別的做法。
- **品質**：怎麼測試、上線後看哪些指標。

> [!TIP]
> 面試時可以這樣說：「我會先問需求並把假設寫下來，再說明資料怎麼流動、哪些在背景執行緒。接著挑一個元件講到實作細節，每個選擇都說明取捨和代價，最後講怎麼測試、上線後看哪些指標。」

> [!FIELD]
> 系統設計時可以自然帶入自己的實務經驗，每次一句就好，重點還是回答題目：
> - 即時資料：社交 App 的即時聊天（Socket.IO）、即時行情 App 的行情推送（Server-Sent Events）。
> - 穩定性：用重構與分階段發布，讓雙平台的 crash-free users 明顯提升。
> - 發布流程：Fastlane 搭配 Codemagic、CircleCI 的自動建置與發布。
> - 測試：把 AI 納入「規劃 → 實作 → review → 修正」的循環，用 AI 撰寫單元測試。

## 常見陷阱

- **一聽到題目就開始畫架構圖。** 沒有先釐清需求和規模，後面的設計就沒有根據。
- **把時間花在後端。** 資料庫、分片、負載平衡不是 Mobile 面試的重點，App 端的資料流和狀態才是。
- **只講一切順利的情況。** 斷線、App 進背景、資料缺漏、錯誤處理，才是交易所 App 最容易出問題的地方。
- **堆名詞。** 「我會用 Clean Architecture、MVVM（Model-View-ViewModel，畫面只負責顯示，由 ViewModel 整理畫面要用的狀態）、Repository Pattern」卻說不出資料怎麼流動，面試官會覺得你只是背了名詞。

## 面試官想聽到的

1. 主動問需求和規模，並且把假設寫下來。
2. 清楚的資料流，以及哪些工作在背景、哪些在主執行緒。
3. 至少一個元件講到實作細節（狀態流程、演算法、資料結構）。
4. 每個選擇都說得出取捨：為什麼這樣選、代價是什麼、什麼條件下會改。
5. 怎麼測試、上線後怎麼監控。
