## 重點講解

這個單元回答八個問題：

1. 開始設計前要先問什麼？
2. 模組要怎麼切？
3. 每個畫面裡的程式碼要怎麼分層？
4. 要不要用 Kotlin Multiplatform 共用程式碼？
5. 設計系統（design system）要包含什麼？
6. 品質和發布流程怎麼建？
7. AI 要放在開發流程的哪裡？
8. 如果你加入團隊，前 90 天會做什麼？

### 1. 開始設計前要先問什麼？

架構是為團隊和產品服務的，所以先問清楚：

- **團隊**：iOS、Android 各有幾個人？之後會不會增加？有沒有專職的 QA（quality assurance，品質保證／測試人員）？
- **現況**：是全部重寫，還是在現有的 App 上逐步改？最低支援的 OS 版本是多少？
- **節奏和要求**：多久發布一次？有哪些法規和稽核的要求？安全等級要多高？

逐步改的做法常被稱為 strangler pattern：新功能用新架構寫，舊的部分一塊一塊換掉，不一次全部重寫。交易所 App 已經在線上營運，通常會選這種做法，風險比較低。

> [!TIP]
> 面試時可以這樣說：「設計架構之前，我會先問團隊有幾個 iOS、Android 工程師、有沒有專職的 QA，也會問是全部重寫還是在現有的 App 上逐步改，以及發布的節奏和法規的要求。交易所 App 已經在線上營運，我會選 strangler pattern，新功能用新架構寫，舊的一塊一塊換掉，風險比較低。」

### 2. 模組要怎麼切？

**結論：依「功能」和「共用的基礎能力」切成兩類模組。功能模組之間不互相依賴，只依賴基礎模組；兩個平台用同一張模組圖，溝通比較容易。**

```text
app（把所有模組組裝起來：依賴注入、畫面導航）
├─ feature-market     行情列表、交易對頁、K 線
├─ feature-trade      下單、訂單、成交紀錄
├─ feature-assets     資產、日圓入出金、加密貨幣入出庫
├─ feature-account    登入、兩步驟驗證、eKYC（線上身分驗證）、設定
├─ core-designsystem  顏色、字體、共用元件、數字的顯示格式
├─ core-network       REST、API 簽名、WebSocket 連線管理、重試
├─ core-data          Repository 的介面、快取
├─ core-security      Keychain／Keystore、生物辨識、憑證綁定、越獄偵測
├─ core-analytics     事件紀錄、log、效能監控
└─ core-testing       測試用的假資料、假實作、錄下來的 WebSocket 訊息
```

規則：

- **feature 模組之間不互相依賴**。例如下單模組不直接 import 行情模組。如果需要從行情頁跳到下單頁，由最外層的 app 模組負責導航（iOS 用 Coordinator，Android 用 Navigation 的 route）。這樣每個功能可以獨立開發、測試，修改時影響範圍也小。
- **iOS** 用 SPM（Swift Package Manager，Apple 官方的套件管理工具）的 local package 切模組；**Android** 用 Gradle 多模組，搭配 convention plugin（把共用的 Gradle 設定集中在一個地方）和 version catalog（集中管理所有套件的版本）。

> [!TIP]
> 面試時可以這樣說：「我會把模組分成功能模組和基礎模組。功能模組彼此不依賴，只依賴基礎模組，導航由 app 層組裝。兩個平台用同一張模組圖，iOS 用 SPM，Android 用 Gradle 多模組。」

### 3. 每個畫面裡的程式碼要怎麼分層？

```text
畫面（SwiftUI／Compose）
  → ViewModel（持有畫面狀態，接收使用者的操作）
    → UseCase（有共用的商業邏輯時才加）
      → Repository（決定資料從哪裡來：網路或快取）
        → DataSource（實際打 API、讀資料庫）
```

- **單向資料流**（UDF，unidirectional data flow）：畫面只做兩件事，顯示 ViewModel 給的狀態、把使用者的操作傳給 ViewModel。狀態只在 ViewModel 裡改，資料只往一個方向流，比較好追蹤和測試。
- **單一資料來源**：行情、訂單、資產各自只有一個 Store（見案例一、二）。
- **依賴注入**（DI，dependency injection：物件需要的東西由外面傳進來，而不是自己建立）：Android 用 Hilt；iOS 用簡單的 container 或 factory。依賴注入讓測試時可以換成假的實作。

> [!TIP]
> 面試時可以這樣說：「每個畫面我會分成畫面、ViewModel、Repository 和 DataSource。畫面只顯示 ViewModel 給的狀態、把操作傳回去，資料單向流動，比較好追蹤和測試。行情、訂單、資產各自只有一個 Store，依賴用注入的方式傳進來，測試時就能換成假的實作。」

### 4. 要不要用 Kotlin Multiplatform 共用程式碼？

Kotlin Multiplatform（KMP）可以用 Kotlin 寫一份邏輯，同時給 iOS 和 Android 使用。

**結論：「兩個平台的結果必須完全一樣」的純邏輯最值得共用，例如金額計算、訂單狀態機；UI 和平台專屬的功能不要共用。建議先拿一個小模組試行，量過再決定要不要擴大。**

| 適合共用 | 不建議共用 |
|---|---|
| 精度和捨入規則、手續費預估 | UI |
| 訂單狀態機、事件順序顛倒時的合併規則 | 平台的安全 API（Keychain／Keystore 的細節） |
| WebSocket 訊息的解析（解壓縮之後的 JSON）、API 簽名 | 推播、生物辨識、NFC 讀取身分證件 |
| 資料模型和輸入檢查 | 已經很穩定、改了反而有風險的既有模組 |

判斷時要考慮的事：

- **一致性的價值**：金額算錯一個平台就是客訴，共用一份邏輯可以保證兩邊一致。
- **團隊能不能維護**：有沒有人能處理 Kotlin/Native 的問題和 iOS 的建置設定？
- **iOS 工程師的使用體驗**：KMP 產生的 Swift 介面不一定好用，例如 Kotlin 的 suspend 函式要透過工具（例如 SKIE）才能變成好用的 Swift async/await。iOS 團隊用得不順，就會排斥。

試行的做法：先挑一個純邏輯、範圍小的模組（例如精度規則），量 iOS 的建置時間有沒有變慢、開發體驗如何，再決定要不要擴大。

> [!TIP]
> 面試時可以這樣說：「KMP 我會用在兩個平台結果必須完全一樣的純邏輯，例如金額計算和訂單狀態機；UI 和平台專屬的功能維持原生。我會先拿精度規則這種小模組試行，量建置時間和 iOS 端的使用體驗，再決定要不要擴大。我用過 KMP，依領域切成多個共用模組，所以知道它的好處和代價。」

### 5. 設計系統要包含什麼？

設計系統（design system）是把顏色、字體、元件的規則集中在一個地方，讓所有畫面長得一致。交易所 App 要特別注意：

- **漲跌的顏色做成設定**：不同地區的習慣不一樣。台灣和中國大陸是「紅漲綠跌」，歐美多是「綠漲紅跌」。日本的交易所 App 常支援多種語言，做成設定才能依地區或使用者的偏好切換；顏色寫死在畫面裡，之後要改就得每個畫面都改。
- **數字用等寬字型**（tabular figures：每個數字寬度一樣），價格一直跳動時，文字寬度不會跟著變。
- **深色模式、使用者調大字體**（iOS 的 Dynamic Type、Android 的字體縮放），以及多種語言的文字長度差異（英文通常比日文長）。
- **數字的顯示規則集中在一處**：價格、數量、百分比的小數位數和格式化，用同一套元件。不要每個畫面各寫一套。

> [!TIP]
> 面試時可以這樣說：「設計系統除了顏色和元件，交易所 App 還要特別處理幾件事：漲跌的顏色做成設定，因為不同地區的習慣不一樣；數字用等寬字型，價格跳動時寬度才不會變；數字的顯示規則集中在一處，所有畫面用同一套元件；還要考慮深色模式、字體放大和多種語言的文字長度。」

### 6. 品質和發布流程怎麼建？

| 階段 | 做什麼 |
|---|---|
| 每個 PR | 程式碼風格檢查（lint）、單元測試、畫面截圖比對（snapshot test）；AI review 只當輔助 |
| 合併後 | 自動建置測試環境（staging）的版本，給內部測試（iOS 的 TestFlight、Android 的內部測試軌） |
| 每天晚上 | 在多台實機（device farm）上跑端到端測試：登入、行情、下單、撤單、入出金 |
| 發布 | 分階段發布（iOS 的 phased release、Android 的 staged rollout：先給一小部分使用者），用 crash-free 比例和關鍵指標決定要不要繼續擴大 |
| 上線後 | Crashlytics 看 crash、效能監控（MetricKit、Firebase Performance）、行情延遲、下單成功率 |

> [!TIP]
> 面試時可以這樣說：「每個 PR 先跑 lint、單元測試和截圖比對；合併後自動建置 staging 版本給內部測試；每天晚上在多台實機上跑登入、行情、下單、撤單、入出金的端到端測試。發布時分階段，先給一小部分使用者，看 crash-free 比例和關鍵指標，再決定要不要繼續擴大；上線後監控 crash、效能、行情延遲和下單成功率。」

### 7. AI 要放在開發流程的哪裡？

- **開發**：用規則檔（CLAUDE.md、AGENTS.md）寫清楚架構規範、模組邊界、測試要求。AI agent 依規則實作，人負責設計和最後的驗收。
- **測試**：AI 產生測試的草稿 → 驗證這些測試真的能抓到錯（例如故意改壞程式，看測試會不會失敗）→ 人工 review。AI 也可以透過 MCP（Model Context Protocol，讓 AI 操作外部工具的協定）操作模擬器做探索式測試、整理失敗的原因。
- **文件**：用 ADR（Architecture Decision Record，架構決策紀錄）寫下「為什麼這樣設計」，讓人和 AI 都看得懂。

> [!TIP]
> 面試時可以這樣說：「AI 我會放在三個地方：開發時用規則檔寫清楚架構規範和模組邊界，AI 依規則實作，人負責設計和驗收；測試時 AI 產生草稿，我會故意改壞程式確認測試真的抓得到錯，再由人 review；文件用 ADR 記錄為什麼這樣設計，讓人和 AI 都看得懂。」

### 8. 如果你加入團隊，前 90 天會做什麼？

- **前 30 天**：讀懂現有的架構和發布流程，從修 bug 開始熟悉程式碼；盤點測試和 CI 的現況。
- **30 到 60 天**：提出模組化和測試策略的 ADR；先改善最痛的一塊（例如行情模組），並建立基本的測試。
- **60 到 90 天**：AI 自動化測試的第一版上線（關鍵流程的端到端測試加上 AI 輔助），有指標可以追蹤效果。

> [!TIP]
> 面試時可以這樣說：「前 30 天我會先讀懂現有架構、修 bug、盤點測試現況；60 天提出模組化和測試策略；90 天讓 AI 自動化測試的第一版上線，並用指標追蹤效果。」

## 常見陷阱

- **一開始就拆成幾十個模組。** 建置設定和維護成本暴增。先依功能切大塊，真的需要再細分。
- **為了共用而用 KMP。** iOS 團隊用得不順、建置變慢，最後兩邊都痛苦。只共用真正需要一致的邏輯。
- **設計系統只做了顏色。** 數字格式每個畫面各寫一套，小數位數不一致。
- **只講架構，不講發布、監控和品質。** 面試官想知道的是「這個架構上線後怎麼確保它是好的」。

## 面試官想聽到的

1. 架構是為團隊和產品服務的：考慮團隊規模、發布速度和品質。
2. KMP 的取捨有具體的判斷標準和試行計畫。
3. 品質和發布流程完整，AI 放在合理的位置，而且有人把關。
4. 加入後的具體計畫。

> [!FIELD]
> 有三個實務經驗可以引用，每個一句就好：
> - 在一個 BLE 智慧鎖 SDK 的專案：以 Kotlin Multiplatform 把 iOS 和 Android 的共用邏輯，依領域（common／user／manager）切成多個模組，兩邊再對應成 Android library module 和 iOS framework。
> - 在一個社交 App：iOS 全面重構（SwiftUI＋UIKit 混合、導入 Swift Concurrency 與 Combine）；Android 一邊開發新功能一邊逐頁重構，依賴注入從 Dagger 遷移到 Hilt。這就是「在線上營運的 App 上逐步改」的實例。
> - 在一個即時行情 App：一個人從零開發到雙平台上架。
