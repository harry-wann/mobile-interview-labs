## 重點講解

這個單元照系統設計的作答順序，回答七個問題：

1. 下單功能有哪些需求？
2. API 長什麼樣子？
3. 整體架構怎麼安排，才能讓每個畫面的數字一致？
4. 一筆訂單有哪些狀態？狀態怎麼變化？
5. 怎麼保證不會重複下單？
6. 資產的數字要怎麼算才不會出錯？
7. 有哪些例外情況？怎麼測試和監控？

### 1. 下單功能有哪些需求？

- **取引所（使用者之間互相成交的市場）的下單**：指値（限價單）、成行（市價單），必要時加上逆指値（停損單）；還有撤單、未成交訂單列表、成交紀錄。
- **資產頁**：日圓和每個幣種的「可用」數量和「凍結」數量。凍結是指已經掛單、暫時不能用的部分。
- **一致性**：下單後，訂單頁、資產頁、交易對頁顯示的數字不能互相矛盾。
- **可靠性**：網路不穩、逾時、使用者連點、App 被系統關掉時，**不能重複下單**，也不能讓使用者以為沒下成功。

> [!TIP]
> 面試時可以這樣說：「下單功能我會先確認有限價、市價，必要時加上停損這幾種訂單，還有撤單、未成交訂單列表和成交紀錄；資產要顯示可用和凍結兩種數量。最重要的兩個需求是一致性，也就是訂單頁、資產頁和交易對頁的數字不能互相矛盾，以及可靠性，網路不穩或 App 被關掉時不能重複下單。」

### 2. API 長什麼樣子？

以一般交易所的形式為例（實際的名稱以各交易所的 API 文件為準）：

- **REST（需要簽名的請求）**：下單、撤單、查詢訂單、查詢資產。下單時帶一個 **client order id**：App 自己產生的訂單編號。以 Huobi 系 API 為例，文件寫明這個編號在 8 小時內必須唯一。
- **注意**：以這套 API 為例，文件沒有「用 client order id 查單筆訂單」的端點。逾時後要確認訂單狀態，得查**未成交訂單列表**和**訂單紀錄**，再從回傳的資料裡比對 `client-order-id`。
- **私有 WebSocket**（`/ws/v2`，要先驗證身分）：推送訂單狀態的變化和資產的變動。
- **限流**：需要簽名的 REST，每個 API key 每秒最多 10 次。

> [!TIP]
> 面試時可以這樣說：「需要簽名的 REST 負責下單、撤單和查詢，私有 WebSocket 負責推送訂單和資產的變化。下單時帶 App 自己產生的 client order id。如果 API 沒有用這個編號查單筆訂單的端點，逾時後就要查未成交訂單列表和訂單紀錄，再比對編號。另外要注意，需要簽名的 REST 每個 API key 每秒最多 10 次。」

### 3. 整體架構怎麼安排，才能讓每個畫面的數字一致？

**結論：訂單和資產各自只存在一個 Store（單一資料來源），所有畫面都只讀 Store；Store 的資料只來自伺服器（REST 回覆和 WebSocket 推送），App 不自己計算最終的數字。**

```text
OrderFormViewModel ── 檢查（精度、最小數量、餘額）→ 確認畫面
        │ 送出（帶 clientOrderId）
OrderRepository    ── REST 下單（重試時一定用同一個 clientOrderId）
        │                          ▲
        ▼                          │ 查詢對帳（逾時、回到前景時）
OrderStore（訂單唯一的資料來源）  ◀── 私有 WebSocket 推送（訂單、資產）
BalanceStore（資產唯一的資料來源）◀──┘
        │
訂單頁／資產頁／交易對頁 ── 都只讀 Store
```

如果每個畫面各自打 API，資產頁和下單頁可能拿到不同時間點的資料，使用者就會看到兩個不一樣的「可用餘額」。

> [!TIP]
> 面試時可以這樣說：「訂單和資產各自只有一個 Store，所有畫面只讀它；Store 的資料只來自伺服器的回覆和推送。這樣不同畫面不會顯示不一樣的數字，App 也不會自己算出和伺服器不同的餘額。」

### 4. 一筆訂單有哪些狀態？狀態怎麼變化？

**結論：把訂單寫成一個狀態機，而且一定要有一個「不確定」（unknown）的狀態，代表「送出去了，但不知道伺服器有沒有收到」。**

```text
draft（填寫中）→ validating（檢查中）→ confirming（確認畫面）→ submitting（送出中）
  submitting 之後有三種結果：
  ├─ accepted（伺服器已接受）→ partiallyFilled（部分成交）→ filled（全部成交，結束）
  │                └──→ canceling（取消中）→ canceled（已取消，結束）
  ├─ rejected（被拒絕，結束，顯示原因）
  └─ unknown（逾時或斷線）→ 查詢對帳 → 歸到上面其中一種
```

**為什麼需要 unknown？** 網路逾時不代表下單失敗：伺服器可能已經收到、也成交了，只是回覆在路上不見了。如果 App 直接顯示「失敗」，使用者再按一次，就變成兩筆訂單。所以逾時時要顯示「確認中」，在背景查詢未成交列表和訂單紀錄，用 client order id 找到這筆訂單，再更新成真正的狀態。**絕對不能自動用一個新的編號重送。**

**事件的順序可能顛倒**：WebSocket 的推送可能比 REST 的回覆更早到；同一筆訂單的舊事件也可能晚到。合併時遵守三條規則：

1. **已成交數量只會增加，不會減少**：收到比較小的成交數量，就是舊事件，忽略。
2. **結束的狀態不能再改**：已經 filled 或 canceled 的訂單，收到 partiallyFilled 的事件也不能退回去。
3. **以伺服器的更新時間或版本號為準**：比較新的才套用。

> [!TIP]
> 面試時可以這樣說：「我會把訂單寫成狀態機，特別加一個 unknown 狀態代表逾時：不知道成功沒有，就顯示確認中，用 client order id 去查詢對帳，絕對不自動用新編號重送。事件可能亂序，所以我規定成交數量只增不減、結束的狀態不能退回、以伺服器的版本為準。」

### 5. 怎麼保證不會重複下單？

**結論：按下送出的那一刻產生一個唯一的 client order id，之後不管重試幾次都用同一個。伺服器看到重複的編號，就知道是同一筆。**

「同一個請求送一次或送很多次，結果都一樣」，這個性質叫做冪等（idempotent）。下單本身不是冪等的（送兩次就是兩筆），加上 client order id 才變成冪等。

具體做法：

1. 使用者按下送出時，產生 `clientOrderId`（例如 UUID），**立刻鎖住送出按鈕**，避免連點。
2. 逾時重試時，帶**同一個** `clientOrderId`。伺服器會認出重複，回傳同一筆訂單，或拒絕重複的請求。
3. **App 被系統關掉的情況**：送出前，先把 `clientOrderId` 和訂單內容存到手機裡（標記為「送出中」）。App 重新開啟時，看到有「送出中」的紀錄，就用它去查詢對帳。

> [!TIP]
> 面試時可以這樣說：「按下送出時產生 client order id 並鎖住按鈕，重試一律用同一個編號，伺服器就能認出是同一筆。送出前先把編號存到本機，就算 App 被關掉，重開後也能對帳。」

### 6. 資產的數字要怎麼算才不會出錯？

**結論：資產一律以伺服器為準，App 不自己計算最終餘額。**

- 下單成功後，凍結的數量由伺服器的推送更新。App 可以先顯示「處理中」，但不要自己用「餘額 − 下單金額」算出新餘額，因為手續費、部分成交、捨入規則，App 很難算得和伺服器一模一樣。
- **回到前景、重新連線後、收到成交事件後**，重新查詢一次資產，和伺服器對齊。
- 所有畫面共用同一個 BalanceStore，避免各自打 API 拿到不同時間點的資料。

> [!TIP]
> 面試時可以這樣說：「資產的數字我一律以伺服器為準，App 不自己用餘額減下單金額去算，因為手續費、部分成交和捨入規則，很難算得和伺服器一模一樣。回到前景、重新連線或收到成交事件之後，我會重新查詢一次資產來對齊，而且所有畫面共用同一個 BalanceStore。」

### 7. 有哪些例外情況？怎麼測試和監控？

| 情況 | 怎麼處理 |
|---|---|
| 使用者連點送出 | 按鈕立刻鎖住，加上同一個 client order id |
| 撤單時剛好成交 | 送出撤單後顯示「取消中」，最後狀態以伺服器為準（可能是部分成交後取消，也可能已經全部成交） |
| 斷線時按下單 | 不排隊、不等連線恢復後自動補送；直接告訴使用者現在無法下單 |
| 市價單的滑價 | 確認畫面顯示預估成交價和滑價提醒；金額大時再多提醒一次 |
| 被限流（HTTP 429） | 依伺服器的 `Retry-After` 等待；畫面告訴使用者稍後再試 |
| 金額 | 一律用 `Decimal`；價格對齊最小跳動單位（tick size），數量對齊最小單位並往下捨去（詳見精度單元） |

**測試**：

- 狀態機的單元測試：列出各種事件順序的組合（REST 先到、WebSocket 先到、重複的事件、結束後又收到舊事件），確認結果都正確。
- 整合測試：在測試環境（staging）真的下單、撤單；模擬網路中斷（iOS 的 Network Link Conditioner、Android 模擬器的網路設定）。

**上線後監控**：下單的延遲、被拒絕的原因分布、**unknown 狀態出現的比例和解決需要的時間**、重複下單的警報。

> [!TIP]
> 面試時可以這樣說：「例外情況我會講幾個：連點要立刻鎖住按鈕；撤單時剛好成交，最後狀態以伺服器為準；斷線時不排隊補送，直接告訴使用者現在無法下單；被限流就依 `Retry-After` 等待。測試重點是狀態機在各種事件順序下的結果；上線後我會監控 unknown 狀態出現的比例和解決需要的時間，以及重複下單的警報。」

### 演練 1：下單之後，三個分頁的可用餘額不一樣（第 3 題）

**檔案**：`L01_SingleSource.swift`（iOS）、`L01_SingleSource.kt`（Android）

**情境**：App 有三個分頁：首頁、資產頁、下單頁，打開 App 時都已經建立好，之後一直留在記憶體裡，每一頁都會顯示「可用餘額」。伺服器上日圓可用 1,000,000、凍結 0。使用者在下單頁送出一張 300,000 円的限價買單：先是下單的 REST 回覆回來（只有下單頁知道；回覆裡只有訂單編號，沒有餘額），接著私有 WebSocket 推送資產變動（可用 700,000、凍結 300,000）。看三個分頁各自顯示的可用餘額。

**怎麼寫**

1. **Bug 版**：每個畫面建立時，各向伺服器要一份可用餘額，存在 `copies` 裡；下單頁收到 REST 回覆後，重新要一次，只更新自己那一份；WebSocket 的推送沒有人處理（`balancePushed` 是空的，已經寫好）。
2. **修正版**：只有一份 `store`：畫面建立時，`store` 還是空的才向伺服器要；推送來了就把 `store` 換成推送來的資料。三個畫面都讀 `store`（`shownAvailable` 已經寫好）。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 首頁和資產頁一直停在 1,000,000，下單頁是 700,000：「最後：首頁 1,000,000／資產頁 1,000,000／下單頁 700,000（伺服器 700,000），2 種不同的數字」 |
| 修正版 | 推送一來，三個分頁一起變：「最後：首頁 700,000／資產頁 700,000／下單頁 700,000（伺服器 700,000），1 種不同的數字」 |

**為什麼**：每個畫面各自打 API、各存一份，就會有「誰在什麼時候更新」的問題：下單頁因為知道自己剛下了單，所以更新了；首頁和資產頁什麼都不知道，要等使用者重新打開，或下一次輪詢，才會對上。使用者看到的是：資產頁說可用 100 萬，下單頁說只剩 70 萬，不知道哪個才是真的。單一資料來源（single source of truth）的做法：資產只在 BalanceStore 裡有一份，資料只來自伺服器（REST 回覆和 WebSocket 推送），所有畫面只讀 Store。下單的 REST 回覆裡沒有餘額，App 也不自己算（見演練 3），所以等伺服器的推送。

### 演練 2：下單那一瞬間，總資產閃過少了 30 萬（第 6 題）

**檔案**：`L02_AtomicBalance.swift`（iOS）、`L02_AtomicBalance.kt`（Android）

**情境**：資產頁顯示「可用」「凍結」和「總額 = 可用 + 凍結」。BalanceStore 一開始是可用 1,000,000、凍結 0。使用者下了 300,000 円的限價買單之後，查詢資產的回覆是一份清單，每一筆是「類型＋數量」：`trade`（可用）700,000 在前，`frozen`（凍結）300,000 在後。Huobi 系 API 的資產查詢常見這種「可用和凍結分成不同筆」的形式，實際的格式和順序以各交易所的 API 文件為準。Store 每次有變動，就通知畫面更新；資產頁每次被通知，都記下當時的總額。

**怎麼寫**

1. **Bug 版**：Store 有 `available`、`frozen` 兩個欄位，各自一改就通知畫面（iOS 用 `didSet`，Android 用 `Delegates.observable`）；`apply` 一筆一筆套用清單。
2. **修正版**：先把整份清單套用到一份新的資產上（可用、凍結一起），全部套完才換掉 Store 裡的資產，通知畫面一次。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 資產頁更新 2 次，總額先掉到 700,000，再彈回 1,000,000：「最後：資產頁一共更新 2 次，看到的總額依序是 700,000 → 1,000,000」 |
| 修正版 | 資產頁只更新 1 次，總額一直是 1,000,000：「最後：資產頁一共更新 1 次，看到的總額依序是 1,000,000」 |

**為什麼**：可用和凍結是同一份資產的兩個部分，真正的總額從頭到尾都是 1,000,000。分開更新的時候，畫面會在「可用已經扣掉、凍結還沒加上」的中間狀態被通知，總額短暫少了 300,000；使用者看到資產閃了一下少一截，會以為出了什麼事。SwiftUI 在同一個 run loop 裡連續改兩個 `@Published`，通常會合併成一次重畫，但 Combine 的 `sink`、跨過 `await` 的更新，以及 Android 用 `combine` 組合兩個 `StateFlow`，都不保證合併。做法很簡單：把會一起變的資料放在同一個值型別（struct 或 data class）裡，整份換掉，畫面一次只會看到完整的一份。

### 演練 3：下單被拒絕了，可用餘額卻一直少 30 萬（第 6 題）

**檔案**：`L03_OptimisticBalance.swift`（iOS）、`L03_OptimisticBalance.kt`（Android）

**情境**：可用餘額 1,000,000 円。使用者在下單頁按下「買入」，要買 300,000 円。送出之後伺服器還沒回覆，畫面要先顯示一些東西；最後伺服器回覆：拒絕（限價超出允許範圍），沒有凍結任何資金，伺服器上的可用餘額還是 1,000,000。

**怎麼寫**

1. **Bug 版**：`tapBuy` 自己把可用餘額減掉下單金額（樂觀更新，optimistic update：先假設會成功，直接改畫面）；`orderRejected` 只把狀態設成「已被拒絕」，沒有把餘額改回來。
2. **修正版**：`tapBuy` 不動餘額（餘額只來自伺服器），只把狀態設成「處理中」；`orderRejected` 把狀態設成「已被拒絕」。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 按下買入就顯示 700,000，被拒絕之後仍是 700,000：「最後：按下買入後顯示 700,000（無狀態）；收到拒絕後顯示 700,000（伺服器 1,000,000）」 |
| 修正版 | 按下買入顯示 1,000,000 和「處理中」，被拒絕之後仍是 1,000,000：「最後：按下買入後顯示 1,000,000（處理中）；收到拒絕後顯示 1,000,000（伺服器 1,000,000）」 |

**為什麼**：樂觀更新要負責每一條失敗的路徑：拒絕、逾時、被取消、網路中斷，每一條都要記得把畫面改回來；漏掉一條，畫面就一直和伺服器差 300,000。更麻煩的是，就算成功，App 算出來的數字也很難和伺服器一模一樣：手續費、部分成交、捨入規則，都會讓最後的餘額不同。所以筆記的做法是：App 可以先顯示「處理中」，但不要自己用「餘額 − 下單金額」算出新餘額，最終的數字等伺服器的推送。聊天室的訊息可以樂觀更新（送出的訊息先顯示在畫面上），因為算錯的代價很低；餘額不行。

### 演練 4：在電梯裡按的買入，走出電梯後自己下出去了（第 7 題）

**檔案**：`L04_OfflineQueue.swift`（iOS）、`L04_OfflineQueue.kt`（Android）

**情境**：使用者在電梯裡（沒有網路）按下「買入 0.01 BTC，限價 10,000,000 円」。下單頁等了 10 秒沒有結果，使用者以為沒下成功，放棄、關掉畫面。一分鐘後走出電梯，網路恢復，這時市價已經跌到 9,800,000 円。看畫面上顯示什麼，以及網路恢復之後，伺服器收到了幾張單。

**怎麼寫**

1. **Bug 版**：沒有網路時，`submit` 把單存進 `queue`，回傳「已送出，等待連線」；`connectionRestored` 把 `queue` 裡的單補送給伺服器。這相當於把網路層設成「等有網路再送」：iOS 的 URLSession 設 `waitsForConnectivity = true`，Android 用 WorkManager 加上網路條件。
2. **修正版**：沒有網路時，`submit` 不排隊，直接回傳「現在無法下單，請確認網路連線」；有網路才送出。

| 版本 | 寫對了會看到什麼 |
|---|---|
| Bug 版 | 畫面顯示「已送出，等待連線」，網路恢復後伺服器自動收到 1 張單：「最後：畫面顯示「已送出，等待連線」；網路恢復後伺服器收到 1 張單」 |
| 修正版 | 畫面顯示「現在無法下單，請確認網路連線」，伺服器沒有收到任何單：「最後：畫面顯示「現在無法下單，請確認網路連線」；網路恢復後伺服器收到 0 張單」 |

**為什麼**：下單是有時效、有副作用的操作。使用者按下去的時候，看的是當時的價格和當時的想法；一分鐘後補送的單，價格已經不是他看到的，而且他可能早就以為沒下成功，甚至在別的地方重新下了一張。行情的訂閱可以在網路恢復後自動補上，因為重複訂閱沒有副作用；下單不行。筆記第 7 題的規則是：斷線時按下單，不排隊、不等連線恢復後自動補送，直接告訴使用者現在無法下單。

第 1 題（需求）、第 2 題（API 的形狀）是說明題，第 7 題的測試與監控（狀態機的事件順序測試、unknown 狀態出現的比例）是流程與度量題，沒有演練。其他題目的 bug，前面的單元已經練過，這個單元不重複：

- **第 4 題**（訂單狀態機、事件亂序）：下單回應不等於成交（Exchange08 演練 1）、累計成交量只增不減（Exchange08 演練 2）、終態不能退回（Exchange08 演練 3）。逾時之後的 unknown 狀態：先查詢再決定重不重送（Platform05 演練 5）、回到前景不重送同一筆委託（Platform01 演練 6）。
- **第 5 題**（不重複下單）：client order id 在按下按鈕時就產生，重送沿用同一個（Exchange08 演練 4）、先鎖住按鈕再開始非同步工作（Platform02 演練 9）。
- **第 6 題**（資產）：本單元的演練 2、3；金額用 `Decimal`、捨入的方向（Exchange02）。「同一筆成交從 REST 和 WebSocket 各收到一次，不能算兩次」的做法是用成交 ID 去重，和 Advanced05 演練 3（重連後伺服器重送最近幾筆）一樣，這裡不重複。
- **第 7 題**的其他例外情況：撤單時剛好成交（Exchange08 演練 5）、被限流（Exchange08 演練 6、7）、市價單的滑價提醒（Exchange01 演練 4）。

## 常見陷阱

- **逾時就顯示「失敗」。** 使用者再按一次，結果下了兩筆單。逾時要顯示「確認中」並查詢對帳。
- **每個畫面各自打 API。** 資產頁和下單頁的可用餘額不一樣。要共用同一個 Store。
- **收到順序顛倒的事件，狀態倒退。** 例如從 filled 退回 partiallyFilled。要有「結束的狀態不能退回」的規則。
- **App 自己算最終餘額。** 手續費和捨入規則很難算得和伺服器一樣，數字會對不上。

## 面試官想聽到的

1. client order id 和冪等，以及逾時（unknown）怎麼處理。
2. 單一資料來源和訂單狀態機。
3. 事件順序顛倒時的合併規則。
4. 使用者體驗：明確顯示「確認中」「取消中」，不讓使用者猜。

> [!FIELD]
> 可以連結社交 App 的即時聊天：聊天訊息也有同樣的問題，送出後網路斷了，不知道對方有沒有收到。用 App 端產生的唯一編號標記每則訊息，伺服器確認後更新同一則，重送時用同一個編號，就不會出現重複的訊息。
> 面試時可以這樣說：「下單的冪等和聊天訊息防重複是同一個概念：App 端產生唯一編號，重試用同一個，逾時就查詢對帳，而不是重送一筆新的。」
