1. 基礎複習:型別系統

1.1 基本型別 vs 參考型別

int a = 10;          // 基本型別(primitive):值直接存在變數裡
Integer b = 10;      // 參考型別(reference):變數存的是物件的位址
基本型別 參考型別
例子 int, double, boolean, char Integer, String, 自訂類別, 陣列
存放內容 值本身 物件的參考(位址)
可否為 null 不行 可以
預設值 0 / false null
放進集合 不行(需自動裝箱) 可以

使用情境:

  • 計算、迴圈計數 → 用基本型別,效能好、不會有 null。
  • 放進 List、Map,或資料庫欄位「可能沒有值」 → 用參考型別(Integer 可以是 null,代表「未填」)。

詳解:== 和 equals() 的差別

String a = new String("BTC");
String b = new String("BTC");

System.out.println(a == b);        // false
System.out.println(a.equals(b));   // true
  • == 問的是:「兩個變數指向同一個物件嗎?」(比較記憶體位址)。a 和 b 是兩次 new,兩個不同的物件 → false。
  • equals() 問的是:「內容一樣嗎?」——前提是該類別有覆寫 equals(String 有)。兩個物件裡裝的都是 "BTC" → true。
  • 基本型別(int、double…)只能用 ==,比的就是值本身。
  • 自訂類別如果沒覆寫 equals,預設行為繼承自 Object——跟 == 一模一樣(比位址)。所以自己的類別要「比內容」,必須覆寫 equals(連同 hashCode,見第 3 章)。

詳解:Integer 的 127/128 陷阱

Integer a = 127, b = 127;
System.out.println(a == b);   // true ←?!
Integer c = 128, d = 128;
System.out.println(c == d);   // false

原因:Java 把 -128~127 的 Integer 物件預先做成快取(IntegerCache)。寫 Integer a = 127 時,拿到的是快取裡同一個物件,所以 ==(比位址)是 true;128 超出快取範圍,每次都建立新物件 → 位址不同 → false。 教訓:包裝型別(Integer、Long…)比較永遠用 equals(),用 == 是埋地雷——測試時數字小都對,上線遇到大數字就錯。

✏️ 隨堂練習:下面程式印出什麼?(解答如下)
String s1 = "hello";
String s2 = "hello";
String s3 = new String("hello");
System.out.println(s1 == s2);        // ?
System.out.println(s1 == s3);        // ?
System.out.println(s1.equals(s3));   // ?

解答:true / false / true。 字串字面值放在「字串常量池」,s1 和 s2 指向同一個物件;new String() 一定建立新物件,所以 == 為 false;equals() 比內容,為 true。

1.2 String、StringBuilder、StringBuffer

// ❌ 迴圈裡用 + 串接:每次都建立新 String 物件
String result = "";
for (int i = 0; i < 1000; i++) result += i;

// ✅ 用 StringBuilder:在同一個緩衝區上修改
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) sb.append(i);
String result2 = sb.toString();

使用情境:

  • String:不可變(immutable),適合當 Map 的 key、多執行緒共享。
  • StringBuilder:單執行緒下大量串接(組 SQL、組 JSON)。
  • StringBuffer:同 StringBuilder 但方法有 synchronized,多執行緒安全(實務上少用,通常用其他並發手段)。

2. 物件導向三大支柱與使用情境

2.1 封裝(Encapsulation)

public class Account {
    private BigDecimal balance = BigDecimal.ZERO;   // 欄位藏起來

    public void deposit(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("金額需為正數");
        balance = balance.add(amount);
    }
    public BigDecimal getBalance() { return balance; }
}

使用情境:保護不變條件(invariant)。例如「餘額不能被外部直接改成負數」——所有修改都必須經過 deposit/withdraw,規則寫在方法裡,外部繞不過去。交易所的錢包餘額就是典型例子。

💡 注意這裡用 BigDecimal 而不是 double:金額運算絕對不用浮點數,因為 0.1 + 0.2 != 0.3(二進位無法精確表示十進位小數)。這在金融業面試是必考題。

2.2 繼承(Inheritance)與多型(Polymorphism)

public abstract class Order {
    protected String symbol;      // 交易對,例如 "BTC/JPY"
    protected BigDecimal amount;
    public abstract BigDecimal estimateCost();   // 子類別各自實作
}

public class MarketOrder extends Order {        // 市價單
    @Override public BigDecimal estimateCost() { return amount.multiply(currentPrice()); }
    private BigDecimal currentPrice() { /* 查詢即時價 */ return BigDecimal.ONE; }
}

public class LimitOrder extends Order {         // 限價單
    private BigDecimal limitPrice;
    @Override public BigDecimal estimateCost() { return amount.multiply(limitPrice); }
}

// 多型:同一個變數,執行期才決定呼叫誰的方法
List<Order> orders = List.of(new MarketOrder(), new LimitOrder());
for (Order o : orders) {
    System.out.println(o.estimateCost());   // 各自跑自己的實作
}

使用情境:同一類東西有共同行為、但做法不同。呼叫端只依賴抽象(Order),新增「停損單」時不用改呼叫端——這就是開閉原則(對擴充開放、對修改封閉)。

詳解:覆寫(Override)vs 多載(Overload)

名字像,其實是兩件完全不同的事:

class Animal {
    void speak() { System.out.println("..."); }
}

class Dog extends Animal {
    @Override
    void speak() { System.out.println("汪!"); }      // 覆寫 Override:
                                                      // 同名「同參數」,把父類別的實作換掉

    void speak(String mood) {                         // 多載 Overload:
        System.out.println("(" + mood + ") 汪!");     // 同名「不同參數」,其實是另一個新方法
    }
}

Animal a = new Dog();   // 變數型別是 Animal,實際物件是 Dog
a.speak();              // 印出「汪!」
  • Override 在執行期(runtime)決定:呼叫 a.speak() 時,JVM 看的是「a 實際上是什麼物件」(是 Dog)→ 跑 Dog 的版本。這叫動態繫結(dynamic binding),多型就是靠它。
  • Overload 在編譯期(compile time)決定:編譯器看你傳的參數型別,直接選定呼叫哪個方法,跟執行期無關。

詳解:抽象類別(abstract class)vs 介面(interface)

抽象類別 介面
表達的概念 「是一種…」(is-a):MarketOrder 是一種 Order 「會做…」(can-do):這個類別會通知人(Notifier)
能有欄位/建構子? ✅ 可以,所以能共享狀態與部分實作 ❌ 不行(只能常數);Java 8 後可有 default 方法帶預設實作
一個類別能接幾個? 只能繼承 1 個 可以實作多個

經驗法則:先想介面——呼叫端依賴介面最靈活(見 2.3 的依賴反轉);真的有一批子類別要共享欄位或部分程式碼(例如 Order 的 symbol、amount),才升級成抽象類別。本章 2.2 的 Order 用抽象類別,正是因為子類別共享 symbol、amount 兩個欄位。

2.3 介面的現代用法

public interface PriceSource {
    BigDecimal latestPrice(String symbol);

    // default 方法:介面也能帶預設實作(Java 8+)
    default boolean isStale(Instant lastUpdate) {
        return Duration.between(lastUpdate, Instant.now()).getSeconds() > 5;
    }
}

使用情境:依賴反轉。Service 依賴 PriceSource 介面,正式環境注入「WebSocket 實作」,單元測試注入「假資料實作」——不用連網路就能測。

✏️ 隨堂練習:設計一個 Notifier 介面,讓系統可以用 Email 或 App 推播通知使用者,寫出介面與兩個實作的骨架。(參考解答如下)
public interface Notifier {
    void notify(String userId, String message);
}

public class EmailNotifier implements Notifier {
    @Override public void notify(String userId, String message) {
        // 查 email、寄信
    }
}

public class PushNotifier implements Notifier {
    @Override public void notify(String userId, String message) {
        // 發 App 推播
    }
}

// 呼叫端只認識介面:
public class AlertService {
    private final Notifier notifier;
    public AlertService(Notifier notifier) { this.notifier = notifier; }  // 建構子注入
    public void priceAlert(String userId, String symbol, BigDecimal price) {
        notifier.notify(userId, symbol + " 已到達 " + price);
    }
}

重點:AlertService 完全不知道通知是怎麼送出去的,之後要加「LINE 通知」只要新增一個實作類別。

3. 集合框架(Collections)——選對容器

3.1 全景圖

Collection
 ├─ List(有序、可重複)    → ArrayList, LinkedList
 ├─ Set (不重複)           → HashSet, LinkedHashSet, TreeSet
 └─ Queue(佇列)           → ArrayDeque, PriorityQueue
Map(key-value,不屬於 Collection)→ HashMap, LinkedHashMap, TreeMap, ConcurrentHashMap

3.2 怎麼選?

需求 選擇 原因
依索引快速讀取、尾端新增 ArrayList 底層是陣列,get(i) 為 O(1)
頻繁在頭尾插入/刪除 ArrayDeque 環狀陣列,兩端 O(1)
去除重複、快速查「有沒有」 HashSet 雜湊查找平均 O(1)
需要排序的不重複集合 TreeSet 紅黑樹,自動排序,O(log n)
key→value 查詢 HashMap 平均 O(1)
需要依 key 排序或範圍查詢 TreeMap 紅黑樹,subMap() 可取範圍
多執行緒共用的 Map ConcurrentHashMap 只鎖單一桶 + 無鎖更新,執行緒安全(原理見 §7.2)
每次都取「最大/最小」 PriorityQueue 堆積(heap),取頂 O(1)、插入 O(log n)

實務情境舉例:

  • 撮合引擎的買賣掛單簿(order book):買單要照價格由高到低 → TreeMap<BigDecimal, List<Order>>。
  • 「這個 userId 今天查過價了嗎」 → HashSet<String>。
  • 快取最新成交價 symbol → price,多執行緒讀寫 → ConcurrentHashMap。

3.3 HashMap 面試必考:運作原理

  1. 對 key 呼叫 hashCode() 算出雜湊值,決定放進哪個「桶(bucket)」。
  2. 同一桶發生碰撞 → 以鏈結串列串起來;Java 8 之後鏈長超過 8 會轉成紅黑樹(避免退化成 O(n))。
  3. 元素數量超過 容量 × 負載因子(預設 0.75) → 擴容為兩倍並重新分配。

因此:自訂類別要當 HashMap 的 key,必須同時覆寫 hashCode() 和 equals(),而且兩者邏輯要一致(equals 相等 → hashCode 必相等)。

✏️ 隨堂練習:為什麼只覆寫 equals() 不覆寫 hashCode(),物件放進 HashSet 後會「找不到」?(解答如下)

HashSet 找元素時先用 hashCode 定位桶,再用 equals 比對。若沒覆寫 hashCode,兩個內容相同的物件會算出不同雜湊值、落在不同桶——根本走不到 equals 那一步,所以 contains() 回傳 false。

3.4 集合底層結構快問快答(「XX 的資料結構是什麼?」系列)

被問「某集合的底層資料結構」時,答案格式:底層結構 → 關鍵機制(擴容/碰撞/排序)→ 一個適用情境。

問題 標準答案
HashMap 的資料結構? 陣列 + 鏈結串列 + 紅黑樹:雜湊定位到陣列的桶;碰撞串成鏈;Java 8 起鏈長 > 8(且桶陣列 ≥ 64)轉紅黑樹;超過容量 × 0.75 擴容兩倍
為什麼 HashMap 容量是 2 的次方? 定位桶用 hash & (容量-1) 取代取餘數(位元運算快),容量是 2 的次方時這兩者等價且雜湊分布均勻
Java 7 和 8 的 HashMap 差異? 7:陣列+鏈結串列、頭插法(並發擴容會成環死迴圈);8:加入紅黑樹、改尾插法、擴容時不重算雜湊只分高低位
HashSet 的資料結構? 內部就是一個 HashMap:元素當 key,value 放一個共用的假物件(PRESENT)。所以特性與 HashMap 完全相同
LinkedHashMap? HashMap + 雙向鏈結串列串起所有節點:保留插入順序(或存取順序)。開存取順序模式 + 覆寫 removeEldestEntry = 現成的 LRU 快取(LRU = Least Recently Used,滿了就淘汰「最久沒被用到」的那筆;高頻考)
TreeMap / TreeSet? 紅黑樹(自平衡 BST):key 有序,增刪查 O(log n),支援範圍查詢(firstKey/tailMap)
ArrayList? 動態陣列:預設容量 10,滿了擴容 1.5 倍(oldCapacity + (oldCapacity >> 1)),用 Arrays.copyOf 搬移;所以已知大小時用 new ArrayList<>(n) 預先給容量
LinkedList? 雙向鏈結串列:同時實作 List 和 Deque;按索引存取 O(n),實務上幾乎都被 ArrayList / ArrayDeque 取代
ArrayDeque? 環形陣列(頭尾指標繞圈):兩端增刪 O(1),當 Stack 和 Queue 都比 LinkedList 快
PriorityQueue? 二元堆積,用陣列存完全二元樹(父 i → 子 2i+1、2i+2):取頂 O(1)、增刪 O(log n)
Hashtable 和 HashMap 差異? Hashtable 全方法 synchronized、不允許 null key/value,是遠古類別;要執行緒安全用 ConcurrentHashMap(鎖粒度小得多)
ConcurrentHashMap? Java 8 起:陣列 + 鏈結串列/紅黑樹,寫入只對單一桶的頭節點加鎖(用 CAS 或 synchronized;CAS 是什麼見 §7.2),讀不加鎖(volatile 讀)——所以併發度高
String 底層? Java 9 起內部是 byte[](之前 char[])+ 編碼標記(Latin-1/UTF-16 壓縮記憶體);不可變,所以能進字串常量池、安全當 key

💡 行動端對照(被問到可以帶一句):Swift 的 Dictionary/Set 也是雜湊表(開放定址法),Array 是動態陣列(copy-on-write);Objective-C 的 NSDictionary/NSArray 是類簇(class cluster),依大小自動換內部實作。原理相通,面試講得出「跨語言都是同一套資料結構」是加分項。

白話走一遍:map.put("BTC", price) 到底發生什麼事?(表格看不懂時讀這段)

HashMap<String, BigDecimal> map = new HashMap<>();   // 內部:一個長度 16 的陣列(預設)
map.put("BTC", price);
  1. 算雜湊(hash):對 key 呼叫 "BTC".hashCode(),得到一個整數,假設是 66086。
  2. 定位格子(bucket/桶):陣列長度 16,要把 66086 塞進 0~15 其中一格。怎麼算?66086 & 15 = 6 → 放進第 6 格。
    • 這裡 & 15 就是表格裡說的 hash & (容量-1):當容量是 2 的次方(16 = 2⁴)時,& (容量-1) 的結果和 % 容量 取餘數完全相同,但位元運算(bitwise AND)比除法快很多——這就是「容量為什麼一定是 2 的次方」的答案。
  3. 放進去:第 6 格是空的 → 直接放。第 6 格已經有東西(碰撞 collision,別的 key 也算到 6)→ 先用 equals 檢查是不是同一個 key(是就覆蓋 value),不是就掛在那格的鏈結串列(linked list)尾端。
  4. 鏈太長就變樹:同一格掛超過 8 個(且整個陣列已 ≥ 64 格),鏈結串列轉成紅黑樹(red-black tree)——因為在 8 個節點的鏈上找東西要逐個比(O(n)),樹只要 O(log n)。
  5. 太滿就搬家(擴容 resize):元素總數超過 16 × 0.75 = 12 時,開一個 32 格的新陣列,所有元素重新分配位置。0.75 這個比例叫負載因子(load factor)——太滿碰撞變多、太空浪費記憶體,0.75 是折衷。

讀取 map.get("BTC") 就是前兩步再走一次:算 hash → 定位到第 6 格 → 在那格的鏈/樹裡用 equals 找。所以平均 O(1)(直接命中格子),最壞 O(log n)(全部擠在同一格的樹裡)。

✏️ 隨堂練習:用 LinkedHashMap 實作一個容量 3 的 LRU 快取,並說明原理。(解答如下)
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true);   // 第三個參數 true = 依「存取順序」排序
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;   // 超過容量時,自動移除最久未使用的
    }
}

原理:LinkedHashMap 在 HashMap 之上用雙向鏈結串列維護順序;存取順序模式下,每次 get 會把節點移到串列尾端,串列頭就是「最久未使用」。put 後會呼叫 removeEldestEntry 決定要不要淘汰頭節點。 手寫版(面試常要求不用 LinkedHashMap):HashMap + 自己維護雙向鏈結串列——正是資料結構章綜合題 1 說的「組合兩個結構各取所長」。

4. 泛型(Generics)

4.1 基礎:型別參數

// 沒有泛型:拿出來要轉型,錯了執行期才爆炸
List list = new ArrayList();
list.add("hello");
Integer n = (Integer) list.get(0);   // 執行期 ClassCastException!

// 有泛型:編譯期就擋下來
List<String> safe = new ArrayList<>();
safe.add("hello");
// safe.add(123);  // ← 編譯錯誤

4.2 自訂泛型類別與方法

// 通用的 API 回應包裝:任何資料型別都能裝
public class ApiResponse<T> {
    private int code;
    private String message;
    private T data;
    public T getData() { return data; }
}

// 泛型方法:<T> 寫在回傳型別前面
public static <T> T firstOrNull(List<T> list) {
    return list.isEmpty() ? null : list.get(0);
}

使用情境:後端 API 統一回傳格式 ApiResponse<UserDto>、ApiResponse<List<OrderDto>>——寫一次包裝類別,所有 API 共用。

4.3 萬用字元(進階)

void printAll(List<? extends Number> nums) { ... }  // 只讀:接受 List<Integer>、List<Double>
void addNumbers(List<? super Integer> list) { ... } // 只寫:接受 List<Integer>、List<Number>、List<Object>

記法 PECS:Producer Extends, Consumer Super——資料「生產者」用 extends(從裡面讀),「消費者」用 super(往裡面寫)。

詳解:型別抹除(type erasure)

泛型是編譯器的檢查工具,檢查完就被「擦掉」——編譯出來的 bytecode 裡沒有 <String> 這種資訊:

List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();

System.out.println(a.getClass() == b.getClass());   // true!
// 執行期兩個都只是 ArrayList,<String>/<Integer> 已經不存在

為什麼這樣設計?為了向下相容:Java 5 才加入泛型,抹除式設計讓新舊程式碼可以混用。

後果(面試常追問「所以泛型不能做什麼?」):

  • 不能 new T()——執行期根本不知道 T 是誰,JVM 無從建立。
  • 不能 T[] arr = new T[10]——同理。
  • 不能 obj instanceof List<String>——執行期沒有 <String> 可以檢查,只能 instanceof List。

5. 例外處理(Exception)

5.1 體系與分類

Throwable
 ├─ Error(JVM 層級,不該接:OutOfMemoryError…)
 └─ Exception
     ├─ Checked(受檢):IOException, SQLException → 編譯器強迫處理

7.3 詳解:volatile vs synchronized

兩者解決的是不同的問題,先看 volatile 能解決什麼:

// 情境:主執行緒想叫工作執行緒停下來
public class Worker {
    private boolean running = true;          // ❌ 沒加 volatile

    public void work() {                     // 工作執行緒跑這個
        while (running) {
            // 做事...
        }
    }
    public void stop() { running = false; }  // 主執行緒呼叫這個
}

直覺上 stop() 之後迴圈就會停,但實際上可能永遠停不下來:每個執行緒有自己的 CPU 快取(cache),工作執行緒可能一直讀自己快取裡的舊值 true,看不到主執行緒寫的 false。這就是可見性問題(visibility problem)。

private volatile boolean running = true;   // ✅ 加 volatile

volatile 的意思是:「這個變數每次都去主記憶體(main memory)讀最新值,寫完立刻同步回去」——改了馬上被所有執行緒看見。適合「開關/旗標(flag)」這種單純的讀和寫。

但 volatile 救不了 count++:

private volatile int count = 0;

count++;   // 看起來一行,其實是三步:
           // ① 讀出 count(例如讀到 5)
           // ② 加 1(算出 6)
           // ③ 寫回 count
// 執行緒 A 和 B 可能「同時」做 ①,都讀到 5,最後都寫回 6 → 加了兩次只多 1
// volatile 只保證「每一步讀寫是最新的」,擋不住「三步中間被插隊」(原子性問題)

要讓「讀→改→寫」整組不被打斷,得用會互斥的工具:synchronized(排隊)或 AtomicInteger.incrementAndGet()(硬體層級的原子指令 CAS)。

一張表總結:

可見性 visibility 原子性 atomicity 代價
volatile ✅ ❌ 極小
synchronized ✅ ✅(整段互斥) 要排隊,較慢
AtomicInteger 等 ✅ ✅(單一變數) 小(無鎖 CAS)

面試一句話版:volatile 只管「看得到最新值」,不管「中間不被插隊」;synchronized 兩個都管。所以旗標用 volatile、計數用 Atomic、複雜的複合操作用 synchronized。

7.4 詳解:死結(Deadlock)

死結 = 兩條(以上)執行緒互相等對方手上的鎖,全部卡死。最小重現:

Object lockA = new Object();
Object lockB = new Object();

// 執行緒 1:先拿 A,再拿 B
new Thread(() -> {
    synchronized (lockA) {
        sleep(100);                    // 故意停一下,讓兩邊都拿到第一把鎖
        synchronized (lockB) { /* ... */ }   // ← 卡在這裡等 B
    }
}).start();

// 執行緒 2:先拿 B,再拿 A(順序相反!)
new Thread(() -> {
    synchronized (lockB) {
        sleep(100);
        synchronized (lockA) { /* ... */ }   // ← 卡在這裡等 A
    }
}).start();
// 結果:執行緒 1 抱著 A 等 B,執行緒 2 抱著 B 等 A → 永遠互等

死結成立需要四個條件同時滿足(面試常要求背,背的時候想上面的例子就不會忘): 1. 互斥(mutual exclusion):鎖一次只能一人拿。 2. 持有並等待(hold and wait):抱著一把鎖,還去等另一把。 3. 不可剝奪(no preemption):不能從別人手上搶鎖。 4. 循環等待(circular wait):你等我、我等你,成一個圈。

破解 = 打破其中任何一個條件,實務上最常用兩招:

  • 固定加鎖順序(打破循環等待):規定全系統「永遠先拿 A 再拿 B」。經典的「兩帳戶互轉帳」題,標準答案是依帳戶 id 排序後加鎖(永遠先鎖 id 小的)。
  • tryLock(逾時)(打破持有並等待):拿不到就放掉手上的鎖、稍後重試,不要死等。

診斷工具:jstack <pid> 印出 thread dump,死結會直接標 Found one Java-level deadlock。

7.5 詳解:執行緒池(Thread Pool)的參數

把執行緒池想成一間餐廳:

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                            // corePoolSize:正職員工 4 人(常駐)
    8,                            // maximumPoolSize:忙不過來最多加到 8 人(含臨時工)
    60, TimeUnit.SECONDS,         // keepAliveTime:臨時工閒 60 秒就下班
    new ArrayBlockingQueue<>(100),// workQueue:候位區,最多排 100 個任務
    new ThreadPoolExecutor.AbortPolicy()  // 拒絕策略:連候位區都滿了怎麼辦
);

任務(task)進來時的決策順序(面試必考,照這個順序講): 1. 正職(core)還有空 → 直接開新執行緒做。 2. 正職全忙 → 任務進候位區(queue)排隊。 3. 候位區也滿了 → 加開臨時工(擴到 maximumPoolSize)。 4. 臨時工也滿了 → 觸發拒絕策略(rejection policy):丟例外(Abort,預設)/ 叫提交者自己做(CallerRuns)/ 默默丟棄(Discard)。

為什麼不用 Executors.newFixedThreadPool() 就好?→ 它的候位區是無上限的 LinkedBlockingQueue,任務堆積時記憶體會被吃光(OOM,Out of Memory:記憶體耗盡,程式直接掛掉)。所以阿里巴巴 Java 規約等實務規範都要求手動 new ThreadPoolExecutor、明確給佇列上限——面試講出這點很加分。

使用情境:行情推播服務要同時處理「WebSocket 收價」與「多個使用者查詢」——收價執行緒寫 ConcurrentHashMap,查詢執行緒讀,不需要全域鎖。

8. JVM 基礎(進階加分題)

JVM(Java Virtual Machine,Java 虛擬機器):執行 Java 程式的那個程式。你寫的 .java 被編譯成 .class 位元組碼(bytecode),由 JVM 載入、執行、管理記憶體——所以「JVM 題」問的其實是「你的程式跑起來之後,底下發生什麼事」。本節三個主題:記憶體怎麼分區、GC(Garbage Collection,垃圾回收:自動找出沒人在用的物件並釋放記憶體)、類別怎麼被載入。

8.1 記憶體區域

┌───────────────────────────────┐
│ 方法區/Metaspace:類別資訊、常量   │ ← 所有執行緒共享
│ 堆(Heap):所有 new 出來的物件     │ ← 所有執行緒共享,GC 主戰場
├───────────────────────────────┤
│ 虛擬機器堆疊(Stack):區域變數、呼叫框 │ ← 每條執行緒一份
│ 程式計數器 PC                    │ ← 每條執行緒一份
└───────────────────────────────┘

8.2 垃圾回收(GC,Garbage Collection)白話版

問題一:怎麼知道哪些物件是垃圾? 從「一定還活著的起點」出發沿著參考走。這些起點叫 GC Roots(正在執行的方法裡的區域變數、static 欄位等)。從它們出發,沿著參考走得到的物件 = 還有人在用;走不到的 = 垃圾。這招叫可達性分析(reachability analysis)。

為什麼不用更直覺的「引用計數」(每個物件記錄有幾個人參考我,歸零就回收)?因為它處理不了循環參考:A 參考 B、B 參考 A,但已經沒有任何外人參考它們——兩個計數都是 1,永遠不歸零,實際上卻全是垃圾。(對照:Objective-C/Swift 用的就是引用計數,所以那邊要自己處理循環參考——見多執行緒章與 Obj-C 章的 weak。)

問題二:為什麼堆要「分代」(generational)? 觀察發現:大多數物件活不久——方法裡 new 的暫時物件,方法一結束就沒人用了。所以把堆分成兩區,用不同策略:

  • 年輕代(Young Generation):新物件的出生地(Eden 區 + 2 個 Survivor 區)。這裡垃圾比例極高,用「把少數活著的搬走,整區直接清空」的複製演算法,很快——這就是 Minor GC。
  • 老年代(Old Generation):在年輕代活過好幾輪的「長壽物件」搬到這裡。垃圾比例低、空間大,收一次比較慢(Major/Full GC)——所以 Full GC 頻繁是效能警訊。

問題三:面試要知道的收集器名字:G1(JDK 9+ 預設:把堆切成小區域逐批收,停頓時間可預測)、ZGC(超低停頓,幾毫秒內)。知道名字和一句話特色即可。

8.3 類別載入與雙親委派(白話版)

類別第一次被用到時才載入,流程:載入 → 驗證 → 準備 → 解析 → 初始化(背順序即可,面試重點在下面)。

雙親委派模型(parent delegation):類別載入器(class loader)收到「幫我載入 java.lang.String」的請求時,不會自己動手,先問上層的父載入器「你能載嗎?」——一層一層往上問到最頂層(Bootstrap,負責核心類別庫);上層能載就用上層的,全都說不行才輪到自己。

為什麼要這麼麻煩?安全:就算有人在你的專案裡偷放一個惡意的 java.lang.String,請求還是會先委派到頂層——頂層早就載入了 JDK 的正牌 String,偽造的那個永遠沒機會被載入。

class Order { List<String> tags; }

                                      // → original.tags 也多了 "urgent"!

Order deep = deepCopy(original);      // 深拷貝(deep copy):連裡面的 List 也複製一份
deep.tags.add("urgent");              // → original 完全不受影響

10. 綜合實作練習

題目:寫一個簡化的「價格警報服務」,綜合本章所有概念。

需求: 1. PriceSource 介面:BigDecimal latestPrice(String symbol)(泛型不需要,但注入要用介面)。 2. AlertRule record:(String symbol, BigDecimal threshold, Direction direction),Direction 是 enum(ABOVE/BELOW)。 3. AlertService: - 用 ConcurrentHashMap<String, List<AlertRule>> 保存規則(key = symbol)。 - check() 方法用 Stream 找出所有被觸發的規則。 - 金額一律 BigDecimal。 4. 用 ScheduledExecutorService 每 3 秒跑一次 check()。

✏️ 參考解答如下
import java.math.BigDecimal;
import java.util.*;
import java.util.concurrent.*;
import java.util.stream.Collectors;

enum Direction { ABOVE, BELOW }

record AlertRule(String symbol, BigDecimal threshold, Direction direction) {
    boolean isTriggered(BigDecimal price) {
        int cmp = price.compareTo(threshold);
        return direction == Direction.ABOVE ? cmp >= 0 : cmp <= 0;
    }
}

interface PriceSource {
    BigDecimal latestPrice(String symbol);
}

class AlertService {
    private final PriceSource priceSource;
    private final ConcurrentHashMap<String, List<AlertRule>> rules = new ConcurrentHashMap<>();

    AlertService(PriceSource priceSource) { this.priceSource = priceSource; }

    void addRule(AlertRule rule) {
        rules.computeIfAbsent(rule.symbol(), k -> new CopyOnWriteArrayList<>()).add(rule);
    }

    List<AlertRule> check() {
        return rules.entrySet().stream()
            .flatMap(e -> {
                BigDecimal price = priceSource.latestPrice(e.getKey());
                return e.getValue().stream().filter(r -> r.isTriggered(price));
            })
            .collect(Collectors.toList());
    }
}

public class Main {
    public static void main(String[] args) {
        PriceSource fake = symbol -> new BigDecimal("1050000");  // Lambda 實作介面(測試用假資料)
        AlertService service = new AlertService(fake);
        service.addRule(new AlertRule("BTC/JPY", new BigDecimal("1000000"), Direction.ABOVE));

        ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor();
        scheduler.scheduleAtFixedRate(
            () -> service.check().forEach(r -> System.out.println("🔔 觸發警報: " + r)),
            0, 3, TimeUnit.SECONDS);
    }
}

對照需求檢查:介面注入 ✅、record + enum ✅、ConcurrentHashMap ✅、Stream ✅、BigDecimal ✅、ScheduledExecutorService ✅。

1. 心智模型:Objective-C 是什麼

(這一節先建立大方向,範例裡的語法第 2 節會從頭一個一個教——第一次看不懂很正常,讀完第 2 節回頭看就通了。)

  • Objective-C = C 語言 + 物件系統。變數、if、for 這些基本語法和 Java 幾乎一樣(都源自 C)。
  • 物件方法的呼叫寫成中括號:[obj doSomething],意思是「對 obj 送出 doSomething 這個訊息」——程式執行到那一刻才去找這個方法的實作(術語叫動態派發 dynamic dispatch)。
  • 一個類別拆成兩個檔案:.h(標頭檔 header,對外公開「我有哪些方法」)+ .m(實作檔 implementation,方法的內容)。Java 一個 class 一個檔案就好,這個分離是新手最先撞到的差異。
// Greeter.h —— 對外公開的介面
#import <Foundation/Foundation.h>

@interface Greeter : NSObject
- (NSString *)greet:(NSString *)name;
@end

// Greeter.m —— 實作
#import "Greeter.h"

@implementation Greeter
- (NSString *)greet:(NSString *)name {
    return [NSString stringWithFormat:@"你好, %@!", name];
}
@end

// 使用
Greeter *g = [[Greeter alloc] init];    // 配置記憶體 + 初始化
NSString *message = [g greet:@"Harry"]; // 送訊息
NSLog(@"%@", message);

對照 Swift:

Swift Objective-C

g.greet(name: "Harry") [g greet:@"Harry"]
"你好 \(name)" [NSString stringWithFormat:@"你好 %@", name]
print(x) NSLog(@"%@", x);

注意:物件變數一定是指標(NSString *),@ 開頭的都是 Objective-C 的擴充(@"字串"、@interface、@[]…)。

2.1 變數宣告與常數

格式和 Java 一樣:型別 名字 = 初始值;(每行結尾要分號)

// --- 字串:字串是「物件」,寫法有兩個新記號 ---

字串那行拆開看,兩個新記號:

  • @"...":Objective-C 的字串字面值。凡是 @ 開頭的都是 Objective-C 對 C 的擴充(之後會看到 @[] 陣列、@interface 類別……)。
  • *(指標):基本型別的變數直接裝「值」;物件的變數裝的是「物件在記憶體裡的位址」,這種變數叫指標(pointer),宣告時名字前面加 *。

2.2 印出:NSLog

// Java 的同一句:String upper = name.toUpperCase();

4. 類別完整寫法:屬性、初始化、方法

// Coin.h
#import <Foundation/Foundation.h>

NS_ASSUME_NONNULL_BEGIN   // 這個範圍內的指標預設 nonnull(給 Swift 混編看的)

@interface Coin : NSObject

@property (nonatomic, copy)   NSString *symbol;     // 字串用 copy
@property (nonatomic, strong) NSNumber *price;      // 物件用 strong
@property (nonatomic, assign) NSInteger rank;       // 基本型別用 assign
@property (nonatomic, assign, getter=isFavorite) BOOL favorite;

// 指定初始化器
- (instancetype)initWithSymbol:(NSString *)symbol price:(NSNumber *)price;

// 類別方法(等同 Swift 的 static/class func),+ 開頭
+ (instancetype)coinWithSymbol:(NSString *)symbol;

- (NSString *)displayText;

@end

NS_ASSUME_NONNULL_END

// Coin.m
#import "Coin.h"

@implementation Coin

- (instancetype)initWithSymbol:(NSString *)symbol price:(NSNumber *)price {
    self = [super init];            // 固定寫法:先呼叫父類,再檢查
    if (self) {
        _symbol = [symbol copy];    // init 裡直接碰底層變數 _symbol,不走 setter
        _price = price;
    }
    return self;
}

+ (instancetype)coinWithSymbol:(NSString *)symbol {
    return [[self alloc] initWithSymbol:symbol price:@0];
}

- (NSString *)displayText {
    return [NSString stringWithFormat:@"%@ ¥%@", self.symbol, self.price];
}

@end

@property 的修飾詞(面試必考):

修飾詞 意義 用在
strong 強參考,持有物件(預設) 一般物件
weak 弱參考,不持有;物件釋放後自動變 nil delegate、避免循環參考
copy 設值時複製一份 NSString、block(防止外部可變物件偷改)
assign 直接賦值,不管記憶體 基本型別(int、BOOL…)
nonatomic 不加鎖,快(幾乎都用這個) 幾乎所有屬性
atomic getter/setter 加鎖(預設但少用) 極少

@property 會自動產生:底層實例變數 _symbol + getter symbol + setter setSymbol:。self.symbol = x 走 setter;_symbol = x 直接改變數。

✏️ 隨堂練習:為什麼 NSString 屬性建議用 copy 而不是 strong?(解答如下)

因為 NSMutableString 是 NSString 的子類別,外部可以傳一個可變字串進來。若用 strong,外部之後修改那個可變字串,你的屬性內容會跟著變(資料被偷改);用 copy 會在設值當下複製一份不可變版本,之後外部怎麼改都影響不到你。

5. 記憶體管理:ARC 與循環參考

Objective-C 用參考計數:每個物件有 retainCount,歸零就釋放。ARC(Automatic Reference Counting)讓編譯器自動插入 retain/release,你不用手寫,但循環參考仍要自己打破(和 Swift 完全相同的概念)。

// 經典循環:A 強參考 B,B 強參考 A → 誰都死不了(記憶體洩漏)
@interface Downloader : NSObject
@property (nonatomic, copy) void (^completion)(NSData *data);
@end

// ❌ self 持有 downloader,block 又捕獲了 self → 循環
self.downloader.completion = ^(NSData *data) {
    [self handleData:data];        // block 強捕獲 self
};

// ✅ weak-strong dance
__weak typeof(self) weakSelf = self;
self.downloader.completion = ^(NSData *data) {
    __strong typeof(weakSelf) strongSelf = weakSelf;  // 進 block 先變回強參考
    if (!strongSelf) return;                           // self 可能已被釋放
    [strongSelf handleData:data];
};

面試常問:

  • delegate 為什麼宣告成 weak?→ 通常「子物件的 delegate 指回父物件」,若用 strong 就形成循環參考。
  • MRC(Manual Reference Counting,手動管理記憶體的舊時代)的 retain/release/autorelease?→ 知道概念即可:ARC 出現之前,工程師要自己手寫「retain(計數 +1)/ release(計數 −1)」而且必須成對,漏寫就洩漏或崩潰;@autoreleasepool 是那個時代留下來、現在仍有用的工具——迴圈內大量產生暫時物件時,用它讓物件即時釋放,不會堆到迴圈結束。

- (void)priceServiceDidDisconnect:(id)service;
@end

7. Block(Objective-C 的閉包)

// 宣告語法(最難記的部分):回傳型別 (^名字)(參數)
void (^simpleBlock)(void) = ^{ NSLog(@"hi"); };
NSInteger (^add)(NSInteger, NSInteger) = ^NSInteger(NSInteger a, NSInteger b) {
    return a + b;
};
add(2, 3);   // 5

// 當方法參數(最常見用法:完成回呼)
- (void)fetchPriceForSymbol:(NSString *)symbol
                 completion:(void (^)(NSNumber * _Nullable price, NSError * _Nullable error))completion;

// 呼叫
[service fetchPriceForSymbol:@"BTC" completion:^(NSNumber *price, NSError *error) {
    if (error) { NSLog(@"失敗: %@", error); return; }
    NSLog(@"價格: %@", price);
}];

// 捕獲外部變數:預設捕獲「值」,要修改需加 __block
__block NSInteger total = 0;
void (^accumulate)(NSInteger) = ^(NSInteger x) { total += x; };
accumulate(10);   // total == 10

記法:宣告 回傳 (^名)(參數)、實作 ^回傳(參數){...}。背不起來很正常,工程師都在查 [goshdarnblocksyntax 這類速查表]——面試能手寫出「completion handler 模式」就夠了。

block 屬性要用 copy:block 建立在堆疊上,copy 把它搬到堆積,否則離開作用域就失效(ARC 下多數情境會自動 copy,但宣告 copy 是明確的慣例)。

9. KVC / KVO 與 NSNotificationCenter

先把兩個縮寫說清楚:

  • KVC = Key-Value Coding(鍵值存取):不呼叫 getter/setter,改用「屬性名字的字串」存取屬性——[coin setValue:x forKey:@"price"] 等於 coin.price = x,但名字是執行期才給的字串。
  • KVO = Key-Value Observing(鍵值觀察):訂閱「某個物件的某個屬性」,屬性一變就收到通知。
// KVC:用字串名字存取屬性(動態特性的展現)
[coin setValue:@16500000 forKey:@"price"];
NSNumber *p = [coin valueForKey:@"price"];

// KVO:觀察屬性變化
[coin addObserver:self forKeyPath:@"price" options:NSKeyValueObservingOptionNew context:nil];

- (void)observeValueForKeyPath:(NSString *)keyPath ofObject:(id)object
                        change:(NSDictionary *)change context:(void *)context {
    if ([keyPath isEqualToString:@"price"]) {
        NSLog(@"價格變了: %@", change[NSKeyValueChangeNewKey]);
    }
}
// ⚠️ dealloc 前必須 removeObserver,否則崩潰(經典事故題)

// NSNotificationCenter:一對多廣播
[[NSNotificationCenter defaultCenter] postNotificationName:@"PriceDidUpdate"
                                                    object:nil
                                                  userInfo:@{@"symbol": @"BTC", @"price": @16500000}];
[[NSNotificationCenter defaultCenter] addObserver:self
                                         selector:@selector(onPriceUpdate:)
                                             name:@"PriceDidUpdate" object:nil];

10. GCD:多執行緒

GCD = Grand Central Dispatch,Apple 的工作佇列框架。心智模型:你不直接操作執行緒,而是把工作(block)丟進佇列(queue),系統負責分配執行緒去執行。佇列分兩種:串列(serial,一次做一件、照順序)與並發(concurrent,多件同時做);另外有一條特殊的主佇列(main queue)= 主執行緒,所有 UI 更新都必須回到這裡。

// 背景做事,完成後回主執行緒更新 UI(最重要的模板,背起來)
dispatch_async(dispatch_get_global_queue(QOS_CLASS_USER_INITIATED, 0), ^{
    NSData *data = [self downloadPrices];        // 背景執行緒
    dispatch_async(dispatch_get_main_queue(), ^{
        [self refreshUIWithData:data];           // 主執行緒(UI 只能在這裡動!)
    });
});

// 串列佇列:保護共享資料(同一時間只有一件事在跑)
dispatch_queue_t serialQueue = dispatch_queue_create("com.app.orders", DISPATCH_QUEUE_SERIAL);
dispatch_async(serialQueue, ^{ /* 安全地修改訂單陣列 */ });

// dispatch_group:等多個非同步工作全部完成
dispatch_group_t group = dispatch_group_create();
dispatch_group_enter(group);
[self fetchBTC:^{ dispatch_group_leave(group); }];
dispatch_group_enter(group);
[self fetchETH:^{ dispatch_group_leave(group); }];
dispatch_group_notify(group, dispatch_get_main_queue(), ^{
    NSLog(@"全部完成,更新畫面");
});

12.3 Service:模擬行情推送(用到:協定+delegate、block、GCD、extension、NSTimer)

// PriceFeedService.h
#import <Foundation/Foundation.h>
#import "Coin.h"
NS_ASSUME_NONNULL_BEGIN

@class PriceFeedService;   // 前向宣告

@protocol PriceFeedServiceDelegate <NSObject>
- (void)priceFeed:(PriceFeedService *)service didUpdateCoin:(Coin *)coin;
@optional
- (void)priceFeedDidStart:(PriceFeedService *)service;
@end

typedef void (^CoinsLoadedBlock)(NSArray<Coin *> *coins);   // block 型別取別名

@interface PriceFeedService : NSObject
@property (nonatomic, weak) id<PriceFeedServiceDelegate> delegate;   // weak 防循環!
- (void)loadInitialCoinsWithCompletion:(CoinsLoadedBlock)completion;
- (void)startStreaming;
- (void)stopStreaming;
@end

NS_ASSUME_NONNULL_END

// PriceFeedService.m
#import "PriceFeedService.h"

@interface PriceFeedService ()                 // Class Extension:私有成員
@property (nonatomic, strong) NSTimer *timer;
@property (nonatomic, strong) NSMutableArray<Coin *> *coins;
@end

@implementation PriceFeedService

- (void)loadInitialCoinsWithCompletion:(CoinsLoadedBlock)completion {
    // GCD:模擬網路請求 —— 背景組資料、回主執行緒回呼
    dispatch_async(dispatch_get_global_queue(QOS_CLASS_USER_INITIATED, 0), ^{
        NSMutableArray<Coin *> *list = [NSMutableArray array];
        NSDictionary<NSString *, NSNumber *> *seed = @{
            @"BTC/JPY": @16500000, @"ETH/JPY": @580000, @"XRP/JPY": @350,
        };
        for (NSString *symbol in seed) {
            [list addObject:[[Coin alloc] initWithSymbol:symbol price:seed[symbol]]];
        }
        [NSThread sleepForTimeInterval:0.5];   // 假裝有網路延遲
        self.coins = list;
        dispatch_async(dispatch_get_main_queue(), ^{
            completion([list copy]);           // 回傳不可變副本(防禦性複製)
        });
    });
}

- (void)startStreaming {
    __weak typeof(self) weakSelf = self;       // weak-strong dance 防循環
    self.timer = [NSTimer scheduledTimerWithTimeInterval:1.0 repeats:YES block:^(NSTimer *t) {
        __strong typeof(weakSelf) strongSelf = weakSelf;
        if (!strongSelf) return;
        [strongSelf tick];
    }];
    if ([self.delegate respondsToSelector:@selector(priceFeedDidStart:)]) {   // @optional 檢查
        [self.delegate priceFeedDidStart:self];
    }
}

- (void)tick {
    if (self.coins.count == 0) return;
    Coin *coin = self.coins[arc4random_uniform((uint32_t)self.coins.count)];
    double delta = ((double)arc4random_uniform(200) - 100.0) / 1000.0;   // ±10%
    double newPrice = coin.price.doubleValue * (1.0 + delta);
    coin.trend = delta > 0 ? PriceTrendUp : (delta < 0 ? PriceTrendDown : PriceTrendFlat);
    coin.price = @(newPrice);                  // 觸發 KVO!
    [self.delegate priceFeed:self didUpdateCoin:coin];   // 通知 delegate
}

- (void)stopStreaming { [self.timer invalidate]; self.timer = nil; }

@end

交易所 App 架構設計:怎麼設計才合理

本章目標:面對「如果請你設計一個交易所 App,你會怎麼設計架構?」這題,能有條理地從需求特性 → 分層 → 模組 → 關鍵技術決策一路講下來。 這題沒有唯一標準答案,面試官看的是你有沒有章法:先講需求與限制,再講取捨。

1. 先講需求特性(回答的開場)

交易所 App 和一般 App 最大的不同,是這四個特性,每一條都直接決定架構:

特性 意義 對架構的影響
即時性 行情每秒多次更新、下單要快 需要 WebSocket 長連線 + 高效 UI 更新策略
正確性 錢不能錯、狀態不能亂 金額用 Decimal、單一資料真相來源、以伺服器為準
安全性 資產、個資 登入與 Token 管理、生物辨識、憑證固定、越獄偵測
穩定性 行情劇烈時流量暴增 斷線重連、降級策略、錯誤處理要是一等公民

面試開場範例:「我會先確認需求:交易所 App 的核心是行情、下單、資產三大功能,特性是即時、正確、安全。所以我的架構會圍繞『一條穩定的即時資料流』和『嚴格的分層隔離』來設計。」

2. 整體分層架構

圖例:🎨 UI 層=畫面與使用者互動|🧠 簡報層=畫面狀態與邏輯(ViewModel)|📦 領域層=業務規則,不依賴任何框架|💾 資料層=決定資料從哪來(網路/快取)|🔌 基礎設施層=網路與儲存的具體實作。箭頭=依賴方向,只能由上往下,下層不知道上層存在。

各層職責與理由

  1. UI 層:只負責畫,不含業務邏輯。iOS 用 SwiftUI/UIKit,Android 用 Jetpack Compose。
  2. 簡報層(MVVM):MVVM = Model-View-ViewModel,一種 UI 架構模式——View(畫面)只負責顯示,ViewModel 負責把 Model(資料)轉成「畫面要的狀態」並處理畫面邏輯。選 MVVM 的理由:
    • 行情是持續的資料流,MVVM 搭配響應式框架(Combine / RxSwift / Kotlin Flow)最自然:資料流進來 → 轉換 → 綁定到 UI。
    • ViewModel 不依賴 UIKit,可以單元測試。
  3. 領域層:純業務規則(「限價單價格必須 > 0」「可用餘額 = 總額 − 凍結」)。不依賴框架,是最穩定、最值得測試的一層。小型 App 可省略,但交易邏輯複雜時這層讓規則只寫一次。
  4. 資料層(Repository 模式):ViewModel 只說「給我 BTC 行情流」,Repository 決定資料來自 WebSocket、REST 還是快取。換掉資料來源不動上面任何一層。
  5. 基礎設施層:WebSocket、HTTP、資料庫的具體實作,被 Repository 注入使用。

💡 這個分層對 Java 後端同學很親切:相當於 Controller → Service → Repository → DAO 的行動端版本,思想完全一樣——依賴抽象、單向依賴、每層只做一件事。

3. 核心難題一:即時行情資料流

交易所 App 架構的靈魂。設計重點:

圖例:實線箭頭=資料推送方向|虛線箭頭=觀察/綁定(響應式)|Note=關鍵策略說明。

面試要講出來的四個決策

  1. WebSocket 而非輪詢:行情高頻更新,HTTP 輪詢(polling,每隔幾秒問一次「有新資料嗎」)延遲高又浪費;WebSocket 是一條保持開著的長連線,由伺服器主動推資料下來。REST API 則指一般的「一問一答」HTTP 請求,本章用它拉歷史資料與快照。
  2. 節流(throttle)與合併:伺服器一秒推几十次,UI 不需要也畫不動。每 100~250ms 合併一次、同交易對只取最新值,UI 更新頻率和資料到達頻率解耦。
  3. 單一真相來源(Single Source of Truth):所有行情進同一個 Store,各頁面訂閱它。避免「列表頁和 K 線頁價格不同步」這種災難。
  4. 斷線重連策略:指數退避(exponential backoff,重試間隔 1s→2s→4s… 翻倍拉長)——如果所有斷線的 App 都每秒狂敲,伺服器剛復活就被打掛(雪崩);重連成功後先用 REST 拉一次快照補上漏掉的資料,再繼續吃增量推送(不然掛單簿會是錯的)。

K 線圖(可銜接自身的圖表實作經驗)

  • 歷史資料 REST 分頁載入 + 最新一根用 WebSocket 即時更新。
  • 渲染:資料量大時用繪圖層(Core Graphics / 自繪 Canvas)而非堆 View;只重繪可見範圍。
  • 手勢(縮放/平移)在 UI 層處理,資料視窗(可見的 N 根)由 ViewModel 計算。

4. 核心難題二:下單流程的正確性

使用者按下「買入」
  → 本地驗證(格式、餘額、最小單位)——快速擋掉明顯錯誤
  → 二次確認畫面(金額大時)
  → 送出(帶客戶端產生的唯一 requestId)
  → 等待伺服器回應
      ├─ 成功:顯示「已送出」,狀態以後續推送為準
      ├─ 失敗:顯示原因(餘額不足/價格偏離…)
      └─ 逾時:顯示「狀態未知」,用 requestId 向伺服器查詢,❌ 絕不自動重送

關鍵觀念(面試加分點):

  • 冪等性(idempotency):下單請求帶唯一 requestId,網路逾時重試也不會重複成交。這是金融 App 和一般 App 最大的差別之一。
  • 狀態以伺服器為準:本地只做「樂觀顯示」(optimistic UI:先假設會成功、畫面先顯示「送出中」,讓操作感覺即時),但訂單真正的狀態(已掛出/部分成交/全部成交)永遠聽伺服器推送,客戶端不自己推算。
  • 金額不用浮點數:iOS 用 Decimal/NSDecimalNumber,Android 用 BigDecimal,傳輸用字串。和 Java 章講的同一個理由。

5. 核心難題三:安全設計

面向 做法
認證 OAuth2(業界標準的授權流程)/ JWT(JSON Web Token,簽過章的登入憑證,伺服器可驗真偽):access token 短效 + refresh token 輪替
Token 保存 iOS Keychain / Android Keystore(系統提供的加密保險箱),絕不放 UserDefaults/SharedPreferences 明文
敏感操作 下單、提幣前再驗證:生物辨識(FaceID/指紋)或交易密碼
傳輸 全程 TLS(Transport Layer Security,HTTPS 底下的加密層)+ 憑證固定(certificate pinning):App 內寫死信任的伺服器憑證,防中間人攻擊
裝置風險 越獄/root 偵測、防截圖(資產頁)、App 切到背景時蓋遮罩
提幣 白名單地址、2FA(Two-Factor Authentication,二階段驗證:密碼之外再加一道,如簡訊或驗證器 App)、風控延遲——多半由後端主導,App 配合流程

6. 模組化與團隊協作

App 規模大了之後,單一專案會編譯慢、多人互相踩。依功能切模組:

圖例:方框=一個獨立編譯的模組|箭頭=依賴方向。規則:功能模組彼此不相依(透過介面/路由溝通),都只依賴核心模組;主模組負責組裝。

好處:編譯快(只編改到的模組)、權責清楚(行情團隊不會改壞交易模組)、可獨立測試。

7. 技術選型速答(面試快問快答用)

問題 建議回答
原生還是跨平台? 交易所核心 App 用原生:即時行情的效能、安全要求(Keychain/生物辨識)、圖表手感都是原生強項。行銷活動頁可用 WebView 混合。

8. 一分鐘總結版(背起來)

「我會採用分層架構 + MVVM:UI、簡報、領域、資料、基礎設施五層,單向依賴。 行情走 WebSocket 單一資料流,經過節流合併進入單一真相來源 Store,各頁面響應式訂閱;斷線用指數退避重連、重連後先拉 REST 快照。 下單重視正確性:金額用 Decimal、請求帶冪等 ID、狀態以伺服器推送為準。 安全上 Token 進 Keychain、TLS 加憑證固定、敏感操作二次驗證。 規模化後依功能模組化,功能模組互不相依、共用核心模組。」

9. 練習題

✏️ 練習 1:使用者反映「行情列表很卡」,你會從哪些方向排查與優化?(參考答案如下)

依資料流一路查: 1. 更新頻率:有沒有節流?是不是每個 tick 都 reload 整個列表?→ 改成 100~250ms 合併 + 只更新變動的列(diff)。 2. 主執行緒:JSON 解析、數字格式化是否在主執行緒做?→ 移到背景,只有「套用到 UI」在主執行緒。 3. Cell 成本:cell 裡有沒有每次都重建 formatter、做複雜排版?→ 重用、預先計算。 4. 過度繪製:價格閃爍動畫是否觸發整列重繪?→ 只動需要的子視圖。 5. 量測:用 Instruments(Time Profiler)找真正的熱點,不要瞎猜。

✏️ 練習 2:App 在電梯裡斷線 30 秒後恢復,期間使用者的掛單已部分成交。畫面要怎麼回到正確狀態?(參考答案如下)
  1. WebSocket 偵測斷線 → 進入重連(指數退避),UI 顯示「連線中」狀態(誠實告知,避免使用者以為價格是最新的)。
  2. 重連成功後不能只繼續聽增量推送(中間漏掉的事件拿不回來): - 用 REST 拉快照:最新行情、該使用者的未成交訂單與餘額。 - 用快照覆蓋本地 Store(單一真相來源的好處:只要更新一處)。
  3. 快照套用後,再開始處理新的增量推送(注意順序:先快照、後增量,或用序號比對丟棄舊事件)。
  4. 部分成交的掛單由快照帶回正確狀態,UI 自動反映——因為所有頁面都訂閱同一個 Store,不需要逐頁修。

1. 陣列(Array)與動態陣列

索引:  0    1    2    3
      ┌────┬────┬────┬────┐
      │ 10 │ 25 │ 37 │ 42 │   ← 記憶體連續
      └────┴────┴────┴────┘
操作 複雜度 原因
按索引讀寫 a[i] O(1) 位址 = 起點 + i × 元素大小,直接算

「均攤 O(1)」(amortized O(1))是什麼意思? 大部分的尾端新增就是放進下一格,O(1);偶爾一次「滿了要搬家」是 O(n)(整批複製到更大的新陣列)。但因為每次擴容都是加倍,搬家的頻率越來越低——把那次 O(n) 的成本「分攤」到之前的每次新增上,平均每次還是 O(1)。這就是「均攤」:偶爾貴一次,平均起來便宜。

  • Java:int[] / ArrayList;Swift:Array(本身就是動態陣列)。
  • 使用情境:讀多寫少、需要隨機存取。90% 的「清單」場景就用它:行情列表、聊天訊息。
  • 快取友善:記憶體連續,CPU 快取命中率高——所以即使複雜度相同,陣列實務上常比鏈結串列快。

二分搜尋(必會手寫)

int binarySearch(int[] a, int target) {
    int lo = 0, hi = a.length - 1;
    while (lo <= hi) {
        int mid = lo + (hi - lo) / 2;      // 防溢位寫法(面試加分)
        if (a[mid] == target) return mid;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

// 必背:反轉鏈結串列(迭代版)
ListNode reverse(ListNode head) {
    ListNode prev = null, curr = head;
    while (curr != null) {
        ListNode next = curr.next;  // 先存下一個
        curr.next = prev;           // 反轉指標
        prev = curr;                // 兩個指標往前走
        curr = next;
    }
    return prev;
}
✏️ 經典題:怎麼判斷鏈結串列有沒有「環」?(解答如下)

快慢指標(Floyd 判圈):慢指標一次走 1 步、快指標一次走 2 步;有環必相遇,無環快指標先到 null。時間 O(n)、空間 O(1)。

boolean hasCycle(ListNode head) {
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;
    }
    return false;
}

另一解:走過的節點丟 HashSet,看過就有環——時間 O(n) 但空間 O(n)。講出兩解與取捨是加分點。

// 必背:括號配對
boolean isValid(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    Map<Character, Character> pairs = Map.of(')', '(', ']', '[', '}', '{');
    for (char c : s.toCharArray()) {
        if (pairs.containsValue(c)) stack.push(c);              // 左括號入堆疊
        else if (stack.isEmpty() || stack.pop() != pairs.get(c)) return false;
    }
    return stack.isEmpty();
}

// 必背:Two Sum(雜湊表思維的代表題)
int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();   // 值 → 索引
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(target - nums[i]);     // 需要的「另一半」出現過嗎?
        if (j != null) return new int[]{j, i};
        seen.put(nums[i], i);
    }
    return new int[0];
}   // O(n) 時間、O(n) 空間;暴力雙迴圈是 O(n²)

// 中序走訪(遞迴)—— BST 會得到排序結果
void inorder(TreeNode node) {
    if (node == null) return;
    inorder(node.left);
    visit(node);
    inorder(node.right);
}

// 層序走訪(BFS,用 Queue)
void levelOrder(TreeNode root) {
    Queue<TreeNode> q = new ArrayDeque<>();
    if (root != null) q.offer(root);
    while (!q.isEmpty()) {
        TreeNode n = q.poll();
        visit(n);
        if (n.left != null) q.offer(n.left);
        if (n.right != null) q.offer(n.right);
    }
}

前序=根左右(複製樹)、中序=左根右(BST 排序)、後序=左右根(先處理子再處理根,如刪除)、層序=一層層(最短路徑類)。

  • 進階名詞(知道用途即可):Dijkstra(帶權最短路徑)、拓撲排序(有向無環圖排先後)。
// BFS 模板(必背)
void bfs(Map<String, List<String>> graph, String start) {
    Set<String> visited = new HashSet<>();
    Queue<String> q = new ArrayDeque<>();
    q.offer(start); visited.add(start);
    while (!q.isEmpty()) {
        String node = q.poll();
        visit(node);
        for (String next : graph.getOrDefault(node, List.of())) {
            if (visited.add(next)) q.offer(next);   // add 回傳 false = 已看過
        }
    }
}

使用情境:幣種兌換路徑(BTC→ETH→JPY 怎麼換最划算=帶權圖最短路徑)、推薦關係、相依解析。

10. 綜合面試題組

✏️ 題 1:設計資料結構,支援 O(1) 的 insert、delete、getRandom(隨機取一個元素)。(解答如下)

組合技:動態陣列 + HashMap。 - 陣列存元素(getRandom:隨機索引 O(1))。 - HashMap 存「元素 → 它在陣列的索引」(insert/delete 定位 O(1))。 - delete 的技巧:把要刪的元素和陣列最後一個交換,再刪尾端(避免中間刪除的 O(n) 搬移)。

這題考的是「單一結構不夠時,組合兩個結構各取所長」——LRU 快取(HashMap+雙向鏈結串列)也是同一思想。

✏️ 題 2:即時成交流中,隨時要查「目前中位數價格」。用什麼結構?(解答如下)

雙堆積:一個最大堆積存較小的一半,一個最小堆積存較大的一半,維持兩堆大小差 ≤ 1。 - 中位數 = 兩個堆頂(或其平均),查詢 O(1)。 - 每筆新成交插入 O(log n)。 排序陣列每次插入要 O(n) 搬移;單一堆積只能拿最值拿不到中位數——雙堆積正是為這種「串流 + 中位數」設計的。

✏️ 題 3:掛單簿要支援:加掛單、撤單(用訂單 ID)、查最高買價、查「價格 ≥ x 的所有賣單」。設計資料結構。(解答如下)

組合: - TreeMap<BigDecimal, Deque<Order>> buyBook(買簿,價格→該價位訂單佇列;同價位先到先成交 = FIFO)。 - 賣簿同理一個 TreeMap。 - HashMap<String, Order> ordersById:撤單 O(1) 定位(Order 內記住自己的價位,從對應 Deque 移除)。 - 最高買價:buyBook.lastKey() O(log n);範圍查詢:sellBook.tailMap(x)。

考點:TreeMap(排序+範圍)與 HashMap(ID 直查)各司其職;以及想到同價位內要保序(FIFO)。

✏️ 題 4:百萬筆歷史成交已按時間排序,找出某個時間區間 [t1, t2] 內的成交筆數,要快。(解答如下)

二分搜尋兩次:找 t1 的「第一個 ≥ t1 的位置」(lower bound)與 t2 的「第一個 > t2 的位置」(upper bound),兩索引相減即筆數。O(log n),不用掃描。 Java:Collections.binarySearch 或手寫 lower/upper bound(手寫更保險,面試官常要求)。 考點:「已排序」三個字就是在暗示二分。

多執行緒安全:Swift / Objective-C / Java / Kotlin 對照

本章目標:把「執行緒安全」這件事講一次通,然後看四個語言各自的工具。主軸是同一個實務場景——交易所 App 的「最新價快取」(行情執行緒高頻寫入、UI 與多處邏輯同時讀取),用四種語言各實作一遍,面試時無論被用哪個語言問,都答得出來。

1. 問題的本質:三件會出錯的事

不管什麼語言,多執行緒出事都是這三類(面試先講這個,展現你懂原理而不是背 API):

問題 說明 經典症狀
原子性(Atomicity) 「讀→改→寫」不是一步完成,中間被插隊 兩個執行緒同時 count++,少加一次
可見性(Visibility) 一個執行緒改了,另一個看到的還是舊值(CPU 快取/編譯器最佳化) 旗標改成 true 了,另一條執行緒的 while 迴圈永遠跑不完
順序性(Ordering) 指令被重排,別的執行緒看到「不合理的中間狀態」 物件還沒初始化完,參考已經被看到

再加上兩個「工具用錯」造成的病:

  • 死結(Deadlock):互相等對方的鎖。四條件:互斥、持有並等待、不可剝奪、循環等待;破解最實用的一招是固定加鎖順序。
  • 競態條件(Race Condition):結果取決於執行順序。「check-then-act」是溫床:if (map 沒有 key) { 放入 } 兩步之間被插隊。

通用解法分三派,四個語言都是這三派的變形: 1. 互斥(鎖):同一時間只有一人能進 → synchronized、NSLock、Mutex。 2. 別共享,排隊:把所有存取丟進同一條串列隊伍 → GCD serial queue、Kotlin 單執行緒 dispatcher、Actor。 3. 不可變/複製:資料根本不會變,就不用保護 → immutable、值型別複製、快照。

2. 共同場景:最新價快取(PriceCache)

需求:

  • update(symbol, price):行情執行緒每秒呼叫數十次(寫)。
  • price(symbol):UI、下單檢查、警報多處同時呼叫(讀,次數遠多於寫)。
  • 要求:讀寫安全、讀取快、不能死結。

這是典型的讀多寫少,最佳策略是「並發讀 + 互斥寫」。下面看各語言。

3.2 PriceCache 實作

// 首選:直接用 ConcurrentHashMap,內部已做分段/CAS 最佳化
public class PriceCache {
    private final ConcurrentHashMap<String, BigDecimal> prices = new ConcurrentHashMap<>();

    public void update(String symbol, BigDecimal price) {
        prices.put(symbol, price);
    }
    public BigDecimal price(String symbol) {
        return prices.get(symbol);
    }
    // 複合操作不要 check-then-act,用原子方法:
    public BigDecimal highest(String symbol, BigDecimal candidate) {
        return prices.merge(symbol, candidate, BigDecimal::max);   // 原子的「讀改寫」
    }
}

// 面試加分版:若需要自己控制,讀寫鎖示範「並發讀+互斥寫」
public class PriceCacheRW {
    private final Map<String, BigDecimal> prices = new HashMap<>();
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();

    public void update(String symbol, BigDecimal price) {
        lock.writeLock().lock();
        try { prices.put(symbol, price); }
        finally { lock.writeLock().unlock(); }     // 一定放 finally!
    }
    public BigDecimal price(String symbol) {
        lock.readLock().lock();
        try { return prices.get(symbol); }
        finally { lock.readLock().unlock(); }
    }
}

3.3 詳解:synchronized 到底鎖了「哪個物件」?

先建立一個觀念:鎖(lock)不是掛在「程式碼」上,是掛在「某個物件」上的。Java 裡每個物件天生自帶一把鎖(術語叫 monitor lock 或 intrinsic lock)。

synchronized 的意思是:「執行這段程式碼之前,先去拿某個物件的鎖;執行完歸還」。別的執行緒(thread)要拿同一把鎖時,就必須排隊等。

所以關鍵問題永遠是:「這段 synchronized,拿的是哪個物件的鎖?」 三種寫法對應三個答案:

public class Counter {
    private int count = 0;

    // 寫法 1:加在「實例方法」(instance method)上
    // → 拿的鎖 = this(「呼叫這個方法的那個物件」)
    public synchronized void add() {
        count++;
    }
    // 上面完全等同於這樣寫:
    public void addSame() {
        synchronized (this) {      // 明寫出來:鎖的是 this
            count++;
        }
    }

    // 寫法 2:加在「靜態方法」(static method)上
    // → 拿的鎖 = Counter.class(整個類別只有一份的 Class 物件)
    public static synchronized void resetAll() {
        // ...
    }
    // 等同於:
    public static void resetAllSame() {
        synchronized (Counter.class) {    // 鎖的是 Class 物件
            // ...
        }
    }

    // 寫法 3:自己準備一個專用的鎖物件(lock object)——實務上最推薦,意圖最清楚
    private final Object lock = new Object();
    public void addWithLock() {
        synchronized (lock) {
            count++;
        }
    }
}

白話比喻:鎖就像廁所的門鎖。synchronized (x) = 「進 x 這一間,把門鎖上」。兩個人進不同間(不同物件的鎖),互不影響;搶同一間(同一把鎖),後到的才需要等。

這就是為什麼「兩個不同物件的 synchronized 方法互不影響」:

Counter a = new Counter();
Counter b = new Counter();

// 情況 1:執行緒 1 呼叫 a.add(),執行緒 2 呼叫 b.add()
// → 不會互相等!執行緒 1 拿的是「a 的鎖」,執行緒 2 拿的是「b 的鎖」,
//   是兩把不同的鎖(兩間不同的廁所)。

// 情況 2:執行緒 1 和執行緒 2 都呼叫 a.add()
// → 會排隊。兩邊搶的都是「a 的鎖」,這才真的有保護效果。

由此推出最重要的實務規則:要保護某份共享資料,所有碰那份資料的程式碼,必須拿同一把鎖。A 方法鎖 this、B 方法鎖另一個物件,等於 A 鎖了前門、B 從後門進來——form 上有 synchronized,實際上沒有保護。

✏️ 隨堂練習:下面的類別執行緒安全嗎?為什麼?(解答如下)
public class Wallet {
    private BigDecimal balance = BigDecimal.ZERO;

    public synchronized void deposit(BigDecimal amount) {
        balance = balance.add(amount);
    }

    public BigDecimal getBalance() {       // ← 注意:沒加 synchronized
        return balance;
    }
}

不安全,有兩個問題: 1. deposit 拿了 this 的鎖,但 getBalance 沒拿任何鎖——讀的那條執行緒不排隊、也沒有可見性(visibility)保證,可能讀到舊值。 2. 修法:getBalance 也加 synchronized(讀寫都過同一把鎖,同時解決互斥與可見性)。

記住口訣:「只鎖寫、不鎖讀」是常見錯誤——同一份資料,讀和寫要用同一把鎖。

3.4 其他 Java 高頻追問(白話版)

Q:ConcurrentHashMap 為什麼比「整個 Map 加一把大鎖」快? 想像一個有 64 個抽屜(bucket)的櫃子。笨方法是「誰要用櫃子,整個櫃子上鎖」(這就是遠古的 Hashtable)——一次只有一個人能用。ConcurrentHashMap(Java 8+)改成「只鎖你正在改的那一個抽屜」(對該 bucket 的第一個節點用 CAS 或 synchronized,CAS 見下一節 3.5):兩條執行緒改不同抽屜,完全不用等;而且讀取(get)根本不上鎖(靠 volatile 讀保證看到最新值)。所以讀多寫少時效能極好。

Q:多執行緒直接用 HashMap 會怎樣? HashMap 的內部操作(放入、擴容搬家)都假設「只有我一個人在動」。兩條執行緒同時 put,可能互相覆蓋對方剛寫的節點(資料遺失)、size() 數字錯亂;Java 7 時代兩條執行緒同時觸發擴容(resize),甚至會把鏈結串列接成環,之後任何一次 get 走到那個環就無限迴圈、CPU 100%(真實生產事故)。結論:多執行緒環境永遠不要裸用 HashMap,改用 ConcurrentHashMap。

✏️ 隨堂練習:這段程式有什麼問題?怎麼修?(解答如下)
private Map<String, User> cache = new ConcurrentHashMap<>();

public User getUser(String id) {
    if (!cache.containsKey(id)) {        // ①
        cache.put(id, loadFromDb(id));   // ②
    }
    return cache.get(id);
}

問題:雖然 map 本身執行緒安全,但 ①② 合起來是 check-then-act 競態——兩個執行緒同時通過 ①,loadFromDb 被做兩次(快取擊穿)。容器安全 ≠ 複合操作安全,這是最重要的觀念。

修法:

return cache.computeIfAbsent(id, this::loadFromDb);   // 整個「查無則算入」是原子的

3.5 詳解:CAS(Compare-And-Swap,比較並交換)

CAS 是一種「不用鎖也能安全更新變數」的技巧,所以叫無鎖(lock-free)操作。它一次做三件事,而且由 CPU 硬體保證這三件事是一個原子動作、中間不會被插隊:

  1. 看一眼記憶體裡的值,是不是還等於「我預期的舊值」(Compare)
  2. 是 → 換成新值(Swap),回報成功
  3. 不是 → 代表有人搶先改過了,什麼都不做,回報失敗(呼叫方通常會重讀最新值再試一次)

白話比喻:你要改共用白板上的數字。鎖的做法是「把整間會議室鎖起來慢慢改」;CAS 的做法是「我記得白板上是 5,走過去的瞬間瞄一眼——還是 5 就直接改成 6;已經變 7(有人先改了)就不改,回去重新讀再試」。

這就是 AtomicInteger 能安全做 count++ 的原因:

AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet();   // 內部大概長這樣:

// 一個不斷重試的迴圈(術語叫 CAS loop):
while (true) {
    int old = count.get();             // ① 讀目前值,例如 5
    int updated = old + 1;             // ② 算新值 6
    if (count.compareAndSet(old, updated)) {   // ③ CAS:「還是 5 嗎?是就改成 6」
        break;                         // 成功,離開
    }
    // 失敗 = 有別的執行緒搶先改了 → 迴圈重來,重新讀最新值再算一次
}

對比普通 count++ 為什麼會錯:它的「讀→加→寫回」三步間可能被插隊,而且寫回時不檢查值有沒有被動過,直接覆蓋。CAS 的關鍵在第 ③ 步:寫回前檢查「還跟我讀到的時候一樣嗎」,不一樣就放棄重試——所以永遠不會蓋掉別人的更新。

跟鎖的取捨(面試加分):

CAS 鎖(synchronized 等)
衝突少時 極快(不排隊、執行緒不掛起) 較慢(有排隊成本)
衝突激烈時 一直重試空轉,浪費 CPU 乖乖排隊反而穩定
能保護的範圍 一個變數的一次更新 任意長的一段程式碼

哪些東西底層是 CAS:Java 的 Atomic* 全家、ConcurrentHashMap 往空桶放值、Kotlin StateFlow.update {}、各語言的無鎖資料結構。

一句話版:CAS 是 CPU 提供的原子指令——「值還等於我預期的舊值,才換成新值,否則失敗重試」,是 Atomic 類別與多數無鎖結構的基礎。

4.2 PriceCache 實作

// 現代 Android 寫法:StateFlow 當單一真相來源,天生執行緒安全
class PriceCache {
    private val _prices = MutableStateFlow<Map<String, BigDecimal>>(emptyMap())
    val prices: StateFlow<Map<String, BigDecimal>> = _prices.asStateFlow()

    fun update(symbol: String, price: BigDecimal) {
        _prices.update { it + (symbol to price) }   // update{} 是原子的 CAS 迴圈
    }
    fun price(symbol: String): BigDecimal? = _prices.value[symbol]
}

// UI(Compose / ViewModel)直接收流,自動在正確執行緒:
viewModelScope.launch {
    cache.prices.collect { map -> render(map["BTC/JPY"]) }
}

// 互斥鎖版本:Mutex 是「掛起」而非「阻塞」,不佔用執行緒
class PriceCacheMutex {
    private val mutex = Mutex()
    private val prices = mutableMapOf<String, BigDecimal>()

    suspend fun update(symbol: String, price: BigDecimal) =
        mutex.withLock { prices[symbol] = price }

    suspend fun price(symbol: String): BigDecimal? =
        mutex.withLock { prices[symbol] }
}

Android 鐵律:UI 只能在主執行緒碰;網路/磁碟不准在主執行緒——主執行緒卡住幾秒,系統會跳出「應用程式無回應」對話框(ANR,Application Not Responding)。模板:

viewModelScope.launch {                        // 預設主執行緒
    val data = withContext(Dispatchers.IO) {   // 切到 IO 執行緒池
        api.fetchTicker("BTC/JPY")
    }
    textView.text = data.price.toString()      // 自動回到主執行緒
}

面試常問:

  • Coroutine 和 Thread 差別?→ 協程是「可掛起的輕量工作」,幾萬個協程可以跑在少數執行緒上;suspend 掛起時不佔用執行緒,等待 IO 時執行緒被釋放去做別的事。
  • Mutex vs synchronized?→ synchronized 阻塞整條執行緒;Mutex.withLock 只掛起協程,執行緒可以去跑別的協程。協程世界用 Mutex。
  • launch vs async?→ launch 射後不理回 Job;async 回 Deferred<T>,await() 拿結果(常用於平行請求再合併)。

5. Objective-C

沒有語言級的 async/await,靠 GCD(Grand Central Dispatch,Apple 的工作佇列框架:把工作丟進佇列 queue,由系統分配執行緒執行)與鎖。Obj-C 章學過 GCD 基礎,這裡進到執行緒安全的核心用法。

5.1 工具箱速覽

工具 解決什麼 備註
GCD serial queue 「排隊」派:天然互斥 最推薦、最不易錯
dispatch_barrier_async 並發佇列上的「並發讀+獨占寫」 本場景的標準解
@synchronized(self) 快速互斥 方便但較慢
NSLock / NSRecursiveLock 傳統鎖 遞迴呼叫用 Recursive
atomic property 單一屬性讀寫原子 不等於執行緒安全(見下)
dispatch_semaphore 限流、等待 也可當鎖用

5.2 PriceCache 實作(concurrent queue + barrier,經典面試題)

@interface PriceCache ()
@property (nonatomic, strong) NSMutableDictionary<NSString *, NSDecimalNumber *> *prices;
@property (nonatomic, strong) dispatch_queue_t queue;
@end

@implementation PriceCache

- (instancetype)init {
    self = [super init];
    if (self) {
        _prices = [NSMutableDictionary dictionary];
        // 並發佇列:多個讀可以同時跑
        _queue = dispatch_queue_create("com.app.pricecache", DISPATCH_QUEUE_CONCURRENT);
    }
    return self;
}

// 讀:同步丟進並發佇列 → 多讀並行,又能拿到回傳值
- (NSDecimalNumber *)priceForSymbol:(NSString *)symbol {
    __block NSDecimalNumber *result = nil;
    dispatch_sync(self.queue, ^{ result = self.prices[symbol]; });
    return result;
}

// 寫:barrier = 等前面的讀全部做完,獨占執行,做完才放行後面
- (void)updateSymbol:(NSString *)symbol price:(NSDecimalNumber *)price {
    dispatch_barrier_async(self.queue, ^{ self.prices[symbol] = price; });
}

@end

為什麼這樣設計(面試要講得出來):

  • 讀用 dispatch_sync 到並發佇列:多個讀互不擋。
  • 寫用 dispatch_barrier_async:柵欄會「排空」佇列後獨占執行——等效於讀寫鎖,但不用管鎖的配對與死結。
  • ⚠️ 死結陷阱:在某佇列上執行的程式碼,再 dispatch_sync 回同一條佇列 = 自己等自己,必死。串列佇列上這是最常見的事故。

5.3 atomic 的真相(高頻考題)

@property (atomic, strong) NSMutableArray *orders;

atomic 只保證 getter/setter 這一步是原子的:不會讀到寫一半的指標。但:

  • [self.orders addObject:x]:先原子地「取出陣列」,再對陣列 addObject——第二步完全沒保護,照樣爆。
  • count++ 類的讀改寫也一樣不安全。

結論:atomic ≠ 執行緒安全,實務上幾乎都寫 nonatomic,安全交給佇列或鎖。

6.2 PriceCache 實作(Actor:現代標準答案)

actor PriceCache {
    private var prices: [String: Decimal] = [:]

    func update(symbol: String, price: Decimal) {
        prices[symbol] = price              // actor 內部,天然安全
    }
    func price(for symbol: String) -> Decimal? {
        prices[symbol]
    }
}

// 使用:跨入 actor 要 await(編譯器強迫你,忘了直接編譯錯誤)
let cache = PriceCache()

Task {
    await cache.update(symbol: "BTC/JPY", price: 16_500_000)
    let p = await cache.price(for: "BTC/JPY")

    await MainActor.run {                   // 更新 UI 回主執行緒
        label.text = p.map { "\($0)" }
    }
}

Actor 的本質:把「GCD 串列佇列保護狀態」做成語言特性——所有進入 actor 的呼叫自動排隊,而且編譯器擋住任何繞過的存取。Obj-C 靠紀律,Swift 靠編譯器,這是演進方向(面試講出這句很加分)。

// GCD 版(舊專案常見,等同 Obj-C 的 barrier 寫法)
final class PriceCacheGCD {
    private var prices: [String: Decimal] = [:]
    private let queue = DispatchQueue(label: "com.app.pricecache", attributes: .concurrent)

    func update(symbol: String, price: Decimal) {
        queue.async(flags: .barrier) { self.prices[symbol] = price }
    }
    func price(for symbol: String) -> Decimal? {
        queue.sync { prices[symbol] }
    }
}

面試常問:

  • @MainActor 是什麼?→ 一個全域 actor,綁定主執行緒;標在 ViewModel/UI 方法上,編譯器保證這些程式碼在主執行緒跑,取代到處手寫 DispatchQueue.main.async。
  • Sendable 是什麼?→ 「可以安全跨並發域傳遞」的標記:值型別、不可變類別天生符合;可變類別要自己保證並標 @unchecked Sendable(等於向編譯器立軍令狀)。
  • Swift 的 struct(值型別)為什麼對執行緒安全有幫助?→ 傳遞時複製,各執行緒改各的副本,從根本上避免共享。這是「不可變/複製」派。

8. 實務事故案例(從症狀反推,面試官最愛)

✏️ 案例 1:App 偶爾閃退,log 顯示 NSMutableArray 在 enumerate 時被修改("Collection was mutated while being enumerated")。怎麼回事?怎麼修?(解答如下)

成因:一條執行緒在 for-in 走訪陣列,另一條同時 add/remove——典型共享可變集合未保護。 修法(擇一): 1. 所有存取集中到一條 serial queue(排隊派,建議)。 2. 走訪前先拷貝快照:NSArray *snapshot = [self.items copy]; 走訪 snapshot(複製派,讀多寫少時好用)。 3. 讀寫全部加同一把鎖(最後手段)。 加分:說明為什麼「偶爾」才閃退——競態只在時序剛好重疊時發生,這正是並發 bug 難查的原因,壓力測試/TSan(Thread Sanitizer)才能穩定重現。

✏️ 案例 2:Android App 在背景執行緒把運算結果設給 TextView,有時正常有時崩潰。為什麼「有時正常」?正確寫法?(解答如下)

成因:UI toolkit 不是執行緒安全的,背景執行緒碰 View 是未定義行為——檢查沒抓到時「碰巧沒事」,抓到就 CalledFromWrongThreadException。 正確寫法(Kotlin):

viewModelScope.launch {
    val result = withContext(Dispatchers.Default) { heavyCompute() }
    textView.text = result   // 回到 Main
}

更好的架構:ViewModel 暴露 StateFlow,UI 收流;背景只改資料流,永遠不直接碰 View。iOS 對應:@MainActor / DispatchQueue.main.async,道理完全相同——所有平台的 UI 框架都是單執行緒模型。

✏️ 案例 3:Java 服務上線後 CPU 正常但部分請求永遠不回應,執行緒 dump 看到兩條執行緒互相 WAITING。是什麼?怎麼預防?(解答如下)

死結:執行緒 A 持有鎖 1 等鎖 2,執行緒 B 持有鎖 2 等鎖 1(循環等待)。 預防: 1. 固定全域加鎖順序(例:永遠先鎖 id 小的帳戶再鎖 id 大的——轉帳題標準答案)。 2. 用 tryLock(timeout) 拿不到就放棄重試,打破「不可剝奪」。 3. 縮小鎖範圍、減少鎖數量,或改用無鎖結構/佇列化。 加分:說出怎麼診斷——jstack 執行緒 dump 會直接標出 "Found one Java-level deadlock"。

✏️ 案例 4(綜合):行情 WebSocket 執行緒更新快取,UI 每秒讀取;上線後發現 iOS 版用 Swift Dictionary 直接讀寫,偶發崩潰(EXC_BAD_ACCESS)。四個語言各給一個你會採用的修法。(解答如下)

Swift 的 Dictionary 非執行緒安全,並發讀寫會直接記憶體錯誤。修法: - Swift:包成 actor PriceCache(首選);舊碼風格則 concurrent queue + barrier。 - Objective-C:concurrent queue + dispatch_barrier_async 寫、dispatch_sync 讀。 - Kotlin/Android:MutableStateFlow<Map<...>> + update{},UI collect;或 ConcurrentHashMap。 - Java 後端:ConcurrentHashMap,複合操作用 compute/merge。 共同點:都是「並發讀 + 獨占/原子寫」,只是語言提供的外衣不同——面試把這句講出來,就證明你懂的是原理。
